# 贷后自助服务平台 逐字稿

> 最后更新：2026-04-09
> 基于简历中的：贷后自助服务平台（C 端） | 马上消费金融股份有限公司 | 前端负责人 & 全栈开发 | 2024.01 - 2024.08

---

## 完整版（2-3分钟）

> 适用场景：「讲讲你最有成就感/印象最深的项目」或「讲讲你的全栈项目」

这个项目是一个面向贷款用户的 C 端自助平台，我是前端负责人，同时负责了后端的整体架构。

说背景。之前用户处理贷后事务——查还款计划、申请展期、上传凭证这些，全都要打客服电话。客服那边每天大量时间都在处理这些重复咨询，用户体验也不好，等电话排队很烦。所以我们做了这个自助平台，让用户自己在手机上就能搞定。

技术选型上，前端用了 React 18 + Next.js 14，后端用的 NestJS + Prisma + SQLite。选 Next.js 是因为 C 端对首屏加载速度要求高，SSR 能把首屏数据直接渲染出来，不用客户端再请求一次。选 NestJS 是因为它有完整的模块化架构，Guard、Interceptor、Decorator 这些机制跟前端的 React 思路比较统一，一个人全栈写起来心智负担小。

性能这块下了不少功夫。首屏加载之前测过，纯客户端渲染 LCP 是 3.2 秒，改成 SSR 加 React Suspense 流式渲染之后降到了 1.1 秒。还款明细列表数据量大，有的用户有几百条记录，用了虚拟滚动，滚动很流畅。图片凭证用了 Next/Image 自动转 WebP 加裁剪，传输体积砍了 60%。

后端接口治理这块，用 NestJS 的 Guard 做了统一鉴权和限流，用 Prisma 的事务和乐观锁处理还款状态并发。还款计划查询这个接口访问量最大，加了 Redis 缓存，QPS 从 200 上到了 1200。

还有一个比较实际的问题：用户不一定愿意下载 App，特别是临时用一下的场景。所以我们做了 PWA，核心流程在微信内置浏览器里就能用，不用跳转到 App。这个对用户留存帮助比较大。

最后是监控，前后端都接了 OpenTelemetry，链路追踪串联起来了，接口慢、报错都能在 Grafana 上直接看到。上线后排查修复了 3 个 P1 级的性能问题，都是靠全链路 Trace 定位到的。

上线后月活 12 万左右，替代了大概 40% 的人工贷后咨询量。

## 简短版（30秒）

> 适用场景：面试官扫简历时快速介绍

我主导了一个面向贷款用户的 C 端自助平台，前后端都负责。前端用 React + Next.js 做 SSR，后端用 NestJS + Prisma + SQLite。首屏加载从 3.2 秒优化到 1.1 秒，后端接口加了 Redis 缓存和乐观锁处理并发。支持 PWA，在微信里就能用不用下载 App。上线后月活 12 万，替代了 40% 的人工贷后咨询。
