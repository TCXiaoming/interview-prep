## Q1：为什么选 Next.js 而不是纯 CRA/Vite 的 CSR 方案？

C 端对首屏加载速度要求高。纯 CSR 的话，用户打开页面要先下载 JS bundle、执行、再发请求拿数据、再渲染，白屏时间长。

Next.js 的优势：
1. **SSR**：服务端渲染首屏 HTML，用户看到内容更快
2. **流式渲染**：React Suspense + Streaming SSR，先返回骨架屏，数据到了再填充，用户感知更快
3. **SSG/ISR**：不常变的页面（如帮助文档）可以静态生成，CDN 缓存
4. **内置优化**：Image 组件自动裁剪转 WebP、字体优化、脚本加载策略
5. **API Routes**：简单接口可以直接写在 Next.js 里，不需要单独部署

我们的场景是 SSR + 动态数据，用户看到的还款计划是实时的，所以用 SSR。帮助中心、常见问题这类页面用 SSG。

## Q2：Next.js 的 App Router 和 Pages Router 有什么区别？为什么选 App Router？

| 对比 | Pages Router | App Router |
|------|-------------|-----------|
| 目录结构 | `pages/` 目录 | `app/` 目录 |
| 数据获取 | `getServerSideProps` / `getStaticProps` | `async` Server Component 直接 await |
| 布局系统 | 手动实现 | 内嵌 Layout（嵌套布局自动保留状态） |
| 流式渲染 | 不支持 | 支持 React Suspense Streaming |
| 路由组织 | 文件即路由 | 文件夹即路由，更灵活 |

选 App Router 的核心原因：
1. Server Component 可以直接在组件里 `await` 数据获取，不用 `getServerSideProps` 这层包装
2. 嵌套 Layout 支持——贷后平台有侧边栏布局，子页面切换时侧边栏不重新加载
3. 流式渲染——还款计划列表可以先显示骨架屏，数据到了再填充

```jsx
// App Router 的 Server Component
export default async function RepaymentPage({ params }) {
  const plan = await getRepaymentPlan(params.id) // 服务端直接查数据库
  return <RepaymentPlan data={plan} />
}
```

## Q3：NestJS 的模块化架构是怎么组织的？

NestJS 的架构和 Angular 类似，用装饰器组织代码：

```
src/
├── app.module.ts          # 根模块
├── modules/
│   ├── user/              # 用户模块
│   │   ├── user.module.ts
│   │   ├── user.controller.ts   # 路由处理
│   │   ├── user.service.ts      # 业务逻辑
│   │   └── user.entity.ts       # 数据模型
│   ├── repayment/         # 还款模块
│   │   ├── repayment.module.ts
│   │   ├── repayment.controller.ts
│   │   └── repayment.service.ts
│   └── auth/              # 鉴权模块
│       ├── auth.module.ts
│       ├── auth.guard.ts
│       └── auth.decorator.ts
```

每个模块声明自己依赖什么（imports）、提供什么（providers）、暴露什么（exports）。DI 容器自动注入依赖，和 bpmn-js 的模块系统类似。

```ts
@Module({
  imports: [PrismaModule, AuthModule],
  controllers: [RepaymentController],
  providers: [RepaymentService],
  exports: [RepaymentService]
})
export class RepaymentModule {}
```

## Q4：Prisma 的乐观锁怎么实现的？

还款状态的并发安全是个关键问题——用户可能在两个设备上同时操作还款。

实现方式：
1. 数据表加 `version` 字段
2. 更新时携带当前 version
3. Prisma 的事务中检查 version 是否匹配

```ts
async repay(orderId: string, amount: number) {
  return this.prisma.$transaction(async (tx) => {
    // 1. 读取当前版本
    const order = await tx.repaymentOrder.findUnique({
      where: { id: orderId }
    })

    // 2. 更新时检查版本号
    const updated = await tx.repaymentOrder.updateMany({
      where: { id: orderId, version: order.version },
      data: {
        status: 'PAID',
        paidAmount: amount,
        version: { increment: 1 }
      }
    })

    // 3. 如果 updated.count === 0，说明 version 被其他请求改过了
    if (updated.count === 0) {
      throw new ConflictException('还款状态已变更，请刷新后重试')
    }
  })
}
```

## Q5：SSR 流式渲染具体怎么做的？

用 React Suspense 把页面拆成多个独立的数据块，先返回骨架屏，数据到了再流式填充：

```jsx
// 还款页面
export default function RepaymentPage() {
  return (
    <div>
      {/* 这块数据快，先返回 */}
      <UserInfo />

      {/* 这块数据慢，先显示骨架屏 */}
      <Suspense fallback={<RepaymentSkeleton />}>
        <RepaymentPlan />  {/* async Server Component */}
      </Suspense>

      {/* 这块也独立加载 */}
      <Suspense fallback={<HistorySkeleton />}>
        <RepaymentHistory />
      </Suspense>
    </div>
  )
}
```

用户看到的效果：页面框架和用户信息立刻出现（< 200ms），还款计划和历史记录的位置先显示骨架屏，数据到了再替换。整体 LCP 从 3.2s 降到 1.1s。

## Q6：前后端怎么统一接口契约？

用 OpenAPI（Swagger）规范：

1. NestJS 装饰器自动生成 Swagger 文档
2. 前端用 `openapi-typescript-codegen` 根据 Swagger JSON 自动生成 TypeScript 类型和请求函数
3. 接口变了重新生成一遍，类型不匹配编译时就能发现

```ts
// NestJS 端：装饰器自动生成文档
@ApiTags('repayment')
@Controller('api/repayment')
export class RepaymentController {
  @Get(':id/plan')
  @ApiResponse({ type: RepaymentPlanDto })
  async getPlan(@Param('id') id: string): Promise<RepaymentPlanDto> {
    return this.repaymentService.getPlan(id)
  }
}
```

```ts
// 前端：自动生成的类型安全请求
const plan = await RepaymentApi.getPlan(orderId) // 返回值有完整类型
```

## Q7：PWA 在微信内置浏览器里能用吗？

微信内置浏览器对 PWA 的支持有限，Service Worker 和离线缓存这些能力不完整。我们的做法是：

1. **核心流程优先保证可用**：还款确认、凭证上传这些核心操作不依赖 PWA 离线能力，只要有网络就能用
2. **PWA Manifest 做渐进增强**：在 Chrome/Safari 等标准浏览器中支持添加到主屏幕、离线缓存
3. **微信内主要解决的是"不用跳 App"的问题**：用户在微信里收到还款提醒，点击链接直接在微信内打开平台操作，不用跳转到浏览器或 App

## Q8：OpenTelemetry 全链路 Trace 怎么串联前后端的？

1. **前端**：用 `@opentelemetry/web` 在每个请求头中注入 `traceparent`（包含 traceId 和 spanId）
2. **后端**：NestJS 用 `@opentelemetry/sdk-trace-node` 拦截请求，从 `traceparent` 头中提取 traceId，继续创建 span
3. **数据库**：Prisma 的 OpenTelemetry 集成，把 SQL 查询也作为 span 记录
4. **上报**：所有 span 通过 OTLP 协议上报到 Jaeger/Tempo，Grafana 展示完整链路

用户报 bug 时，我可以从 Grafana 上看到：
```
用户点击还款 → [前端 120ms] → API 请求 → [NestJS Guard 5ms] → [Service 20ms] → [Prisma SQL 45ms] → [Redis 缓存命中] → 响应
```

之前排查的一个 P1 问题就是这样定位的：还款接口偶尔要 3 秒，Trace 显示 Prisma 的一次查询要 2.8 秒，发现是缺了一个索引。

## Q9：你的全栈项目里，前后端是怎么联调的？

1. **开发阶段**：NestJS 启动在 3001 端口，Next.js 启动在 3000 端口，通过 `next.config.js` 的 `rewrites` 把 `/api/*` 代理到 3001
2. **接口定义**：NestJS 写好接口后用 Swagger 自动生成文档，前端根据文档生成类型和请求代码
3. **Mock 阶段**：后端没写好的接口，前端用 MSW（Mock Service Worker）拦截请求返回假数据，不阻塞前端开发
4. **联调阶段**：后端部署到测试环境，前端直接请求测试环境接口

## Q10：一个人做全栈，和前后端分离比，有什么实际体感？

优势：
- **上下文切换少**：不用等后端接口，前后端可以并行写
- **接口设计更合理**：自己既写接口又消费接口，设计时会更考虑前端需要什么数据结构
- **问题排查快**：接口慢了，直接看后端代码，不用等后端同学排期

劣势：
- **精力分散**：既要考虑前端渲染性能，又要考虑后端并发安全，容易顾此失彼
- **代码质量**：没有别人 Review 自己的后端代码，容易有盲区

所以我给自己定了个规矩：后端代码也走一遍 Code Review 流程，找组里后端经验多的同事帮忙看。
