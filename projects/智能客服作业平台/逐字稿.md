## 完整版（2-3分钟）

> 适用场景：「讲讲你最有成就感/印象最深的项目」

这个项目是我在马上消费金融负责的客服核心作业平台，我是前端负责人，从技术选型到架构设计都是我主导的。

面向人工客服的作业平台，集成了客服作业的管理、分配、执行、监控等功能。

先说背景。当时这个系统是一个比较老的单体应用，Vue 2.6，没有 TypeScript，十几个人在同一个仓库里开发。问题很明显：代码耦合严重，一个人改了某个模块，另一个人的功能可能就挂了。更麻烦的是发布——哪怕只改了一行代码，也要整个应用重新发布，出了问题也要整体回滚，对业务影响很大。

所以我做了两件事：技术栈升级和架构演进。

技术栈这块，我想引入 TypeScript，但阻力不小。团队之前完全没用过 TS，而且 Vue 2.6 的 Options API 对 TS 支持很差，强推的话体验会很糟糕。我的做法是先做分享，让大家感受到类型系统的好处——特别是配合 VS Code，代码提示会准很多，写起来效率确实高。然后我借着 Vue 2.6 升级到 2.7 的机会，因为 2.7 开始支持 Composition API，TS 才能真正发挥出来。我先自己重构了一个业务模块作为样板，分享给团队，大家看到效果之后接受度就高多了。后来整体开发效率提升了大概 30%，主要体现在需求消化速度上。

架构这块，我把单体应用拆成了微前端，用的是乾坤，按业务域和迭代频次拆了 6 个主子应用。拆完之后每个子应用可以独立部署，出问题只回滚那一个，其他的不受影响。

拆的过程中踩了一个坑——子应用之间的通信。乾坤自带 initGlobalState，但我们没用它，主要是担心全局状态耦合太重，而且有内存泄漏的风险。后来我们自己基于 Event Bus 做了一套事件通信，解耦效果更好。

另一块我花了很多精力的是稳定性治理。当时系统的无崩溃会话率只有 97%，用户偶尔会遇到页面崩溃。我引入了 Sentry 做前端监控，然后开始排查内存泄漏。

排查过程挺有意思的。我用 Chrome DevTools 的 Heap Snapshot 对比不同版本的内存快照，找到增量最多的对象。有一个问题让我印象很深：代码里明明调用了 `window.removeEventListener`，但内存就是没释放。后来仔细看才发现，注销时传的回调函数和注册时的不是同一个引用——注册时用的是匿名函数，注销当然不生效。这种问题在老代码里很常见，改起来也不复杂，但找到它需要耐心。

修完之后我们建立了稳定性运营机制，每两周开一次例会，持续跟踪 Sentry 上报的问题。经过大概四五个迭代，无崩溃会话率从 97% 提升到了 99.999%。

整个过程大概用了半年多，现在回头看，当时慢慢推的方式反而是对的，强推的话团队接受不了，反而会出问题。

## 简短版（30秒）

> 适用场景：面试官扫简历时快速介绍

我在马上消费金融负责客服核心作业平台的前端建设。主要做了两件事：一是把老的单体应用改造成微前端架构，拆了 6 个子应用，实现独立部署和回滚；二是引入 Sentry 做稳定性治理，排查修复了内存泄漏问题，无崩溃会话率从 97% 提升到 99.999%。同时主导了 Vue 2.7 + TypeScript 的技术栈升级，团队开发效率提升了约 30%。
