# Webpack 原理与优化

## 核心概念

### Webpack 构建流程

```
初始化参数 → 开始编译 → 确定入口 → 编译模块（Loader）→ 完成编译
    → 输出资源（Plugin）→ 完成输出 → 写入文件系统
```

1. **初始化** — 读取配置，合并默认参数，实例化 Compiler
2. **编译** — 从 entry 出发，调用 Loader 将模块转为 AST，分析依赖
3. **依赖图构建** — 递归解析所有依赖，构建模块依赖图
4. **生成 chunks** — 根据入口和动态导入，将模块分组为 chunks
5. **输出** — 将 chunks 转换为文件，写入 output 目录

### Loader

**本质：** 一个函数，接收源码，返回转换后的源码。

**执行顺序：** 从右到左（pitch loader 从左到右）。

```js
// 简单的 Loader 示例：给 JS 文件加注释
module.exports = function(source) {
  return `/* Generated at ${new Date().toISOString()} */\n${source}`;
};
```

**常用 Loader：**
- `babel-loader` — ES6+ 转 ES5
- `css-loader` — 解析 CSS 中的 `@import` 和 `url()`
- `style-loader` — 将 CSS 注入 DOM
- `ts-loader` / `esbuild-loader` — TypeScript 编译
- `file-loader` / `url-loader` / `asset module` — 处理文件资源

### Plugin

**本质：** 一个类，实现 `apply` 方法，通过钩子介入构建流程。

```js
// 简单的 Plugin 示例：打包完成后输出提示
class DonePlugin {
  apply(compiler) {
    compiler.hooks.done.tap('DonePlugin', (stats) => {
      console.log('Build done! Time:', stats.endTime - stats.startTime, 'ms');
    });
  }
}
```

**常用 Plugin：**
- `HtmlWebpackPlugin` — 生成 HTML 文件
- `MiniCssExtractPlugin` — CSS 提取为独立文件
- `TerserWebpackPlugin` — JS 压缩
- `SplitChunksPlugin` — 代码分割（Webpack 内置）
- `DefinePlugin` — 定义全局常量
- `ProvidePlugin` — 自动加载模块（如 `$` → jQuery）

### 自定义 Loader 设计

Loader 的本质：一个导出为函数的模块，接收源码字符串（或 Buffer），返回转换后的代码。

**基本结构：**
```js
// markdown-loader.js
const marked = require('marked');

module.exports = function(source) {
  const html = marked.parse(source);      // Markdown → HTML
  return `module.exports = ${JSON.stringify(html)}`; // 返回 JS 模块
  // 或者: export default html (ESM)
};
```

**Loader 的输入/输出：**
- **输入**：文件内容（string 或 Buffer）
- **输出**：处理后的 JS 代码（或者下一个 Loader 能处理的内容）

**链式调用**：Loader 从右到左执行
```js
use: ['style-loader', 'css-loader', 'sass-loader']
// 先 sass-loader(scss→css) → css-loader(解析@import/url) → style-loader(注入DOM)
```

**关键 API：**
- `this.callback(err, result)` — 替代 return，可返回多个值
- `this.async()` — 异步 Loader，返回回调
- `this.resourcePath` — 当前文件的绝对路径
- `this.query` — Loader 的配置参数

**常见模式：**
```js
module.exports = function(source) {
  const options = this.getOptions(); // 获取 loader 配置参数
  const result = transform(source, options);
  return `module.exports = ${JSON.stringify(result)}`;
};
```

Loader 和 Plugin 的对比见下方常见追问。

### 模块解析原理

Webpack 使用 enhanced-resolve 做模块解析：
```
require('./utils')
→ 解析为绝对路径
→ 尝试 utils.js、utils.ts
→ 尝试 utils/index.js、utils/index.ts
→ 查找 package.json 的 main/module/exports 字段
→ 查找 node_modules
```

### 代码分割（SplitChunks）

```js
optimization: {
  splitChunks: {
    chunks: 'all',            // 同时分割同步和异步模块
    cacheGroups: {
      vendor: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendor',
        priority: 10,
      },
      common: {
        minChunks: 2,         // 被至少 2 个 chunk 引用
        priority: 5,
        reuseExistingChunk: true,
      },
    },
  },
}
```

**分割逻辑：**
1. `node_modules` 中的模块 → vendor chunk（第三方库）
2. 被多个 chunk 共享的模块 → common chunk（公共模块）
3. 动态 `import()` → 独立 chunk（按需加载）

## 优化手段

### 构建速度优化

| 手段 | 原理 | 配置 |
|---|---|---|
| 缩小搜索范围 | 减少 Loader 处理的文件 | `resolve.extensions`、`module.rules.exclude` |
| 多线程构建 | 并行编译模块 | `thread-loader`、`esbuild-loader` |
| 缓存 | 二次构建跳过未变化的模块 | `cache: { type: 'filesystem' }` |
| DLL（旧方案） | 预编译不常变化的库 | `DllPlugin` + `DllReferencePlugin`（Vite 时代已不推荐） |

### 构建产物优化

| 手段 | 原理 |
|---|---|
| Tree Shaking | 消除未使用的导出（需 ESM） |
| Scope Hoisting | 将模块合并到一个函数中，减少闭包 |
| 压缩 | Terser 压缩 JS，cssnano 压缩 CSS |
| 按需加载 | 动态 `import()` 实现路由级代码分割 |
| CDN | 大型稳定库用 externals 排除，通过 CDN 引入 |

### 打包分析

```bash
# 使用 webpack-bundle-analyzer
npx webpack --profile --json > stats.json
npx webpack-bundle-analyzer stats.json
```

重点关注：
- 体积异常大的模块（可能引入了全量依赖，如 `import _ from 'lodash'`）
- 重复打包的模块（多个 chunk 中重复包含同一模块）
- 不应该被打包的资源（大型二进制文件、mock 数据）

## 常见追问

### Q: Loader 和 Plugin 的区别？

**回答要点：**
- **Loader** — 模块转换器，在模块加载阶段将文件内容转为 JS 可处理的格式。作用于单个文件。
- **Plugin** — 构建流程干预者，通过 Tapable 钩子在构建各阶段执行逻辑。作用于整个构建过程。

类比：Loader 是流水线上的工人，负责加工单个零件；Plugin 是流水线上的检查站，负责全局性的处理。

### Q: Webpack 的热更新（HMR）原理？

**回答要点：**
1. 启动时创建 WebSocket 连接，WebpackDevServer 作为服务端
2. 文件变化后，Webpack 增量编译变化的模块
3. 编译完成通过 WebSocket 通知客户端
4. 客户端收到通知后，通过 HMR Runtime 请求更新的模块
5. 如果模块有 `module.hot.accept` 回调就执行，否则向上冒泡找能处理的父模块
6. 都找不到就整页刷新

关键点：React/Vue 的 HMR 都是通过 `module.hot.accept` 实现的，框架的 Loader 会自动注入这段代码。

### Q: 为什么 Vite 比 Webpack 快这么多？

**回答要点：**
- **开发模式不用打包** — Vite 用 ESM，浏览器直接请求单个模块，不需要全量打包
- **esbuild 预构建** — 依赖用 esbuild 预构建（Go 写的，比 JS 快 10-100 倍）
- **按需编译** — 只编译当前页面需要的模块，不是全量编译
- **HMR 更快** — 只需要让变化的模块失效，不需要重新构建整个 bundle

但 Vite 生产构建用 Rollup，某些复杂场景（CommonJS、动态导入）Rollup 支持不如 Webpack 灵活。

## 回答要点总结

1. 构建流程要能说清楚 — 从入口到输出的完整链路
2. Loader vs Plugin 的区别是必问题
3. 优化手段要分"构建速度"和"构建产物"两个维度
4. 了解 Vite vs Webpack 的差异是加分项
