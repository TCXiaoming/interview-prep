# 技术选型思路

## 核心概念

### 技术选型的决策框架

```
需求约束 → 候选方案 → 多维对比 → 做出决策 → 验证假设
                                        ↓
                               持续评估，必要时调整
```

### 选型的关键维度

| 维度 | 关注点 |
|---|---|
| 功能匹配度 | 能否满足当前需求，覆盖多少场景 |
| 团队熟悉度 | 团队有多少人用过、学习曲线多陡 |
| 社区与生态 | GitHub stars、npm 下载量、issue 响应速度、插件丰富度 |
| 性能 | 包大小、运行时性能、构建速度 |
| 长期维护性 | 是否有大公司/社区长期维护、版本更新频率 |
| 招聘难度 | 市面上有多少人熟悉这个技术栈 |
| 迁移成本 | 如果将来要换，迁移成本有多大 |

### 常见选型场景与思考

#### 框架选型：React vs Vue

| 维度 | React | Vue |
|---|---|---|
| 学习曲线 | 偏陡（JSX + Hooks 思维转换） | 偏平缓（模板语法直观） |
| 生态丰富度 | 最丰富 | 丰富但略少 |
| 类型支持 | 原生支持好 | Vue 3 明显改善 |
| 灵活度 | 高（只管 View 层） | 中（官方全家桶） |
| 招聘 | 市场最大 | 国内市场大 |

**决策逻辑：** 没有绝对的好坏，看团队和业务。如果是新团队、新项目，React 的生态和人才池更广。如果是 Vue 背景的团队，Vue 3 是更务实的选择。

#### 构建工具：Vite vs Webpack

| 维度 | Vite | Webpack |
|---|---|---|
| 开发启动 | 极快（ESM + esbuild） | 慢（全量打包） |
| HMR | 毫秒级 | 随项目变大变慢 |
| 生产构建 | Rollup/esbuild | Webpack |
| 插件生态 | 快速成长但还不够成熟 | 最成熟 |
| 复杂场景 | 有些 SSR/微前端场景支持不够 | 几乎什么都能做 |

**决策逻辑：** 新项目首选 Vite，开发体验好太多。老项目如果 Webpack 配置已经很完善，迁移成本不一定值得。微前端场景如果用 Webpack Module Federation，就继续用 Webpack。

#### 状态管理：选什么？

- **简单场景**（组件间少量共享）→ Context + useReducer 或 Zustand
- **中等场景**（多模块、异步数据）→ Zustand 或 Redux Toolkit
- **复杂场景**（大量异步、缓存、乐观更新）→ React Query / SWR + Zustand
- **Vue 项目** → Pinia（Vue 3 官方推荐）

**决策逻辑：** 不要为了用而用。大部分项目 Zustand 就够了，不需要 Redux 的模板代码。如果服务端状态多（列表、分页、缓存），React Query 比任何客户端状态管理都好用。

#### 接口层：Axios vs fetch + 封装

- **Axios**：拦截器成熟、取消请求方便、浏览器兼容好
- **fetch + 封装**：原生 API、配合 React Query/SWR 更自然、不需要额外依赖

**决策逻辑：** 如果项目用了 React Query/SWR，它们本身就处理了缓存、重试、乐观更新，搭配原生 fetch 就够了，不需要再套一层 Axios。如果项目比较传统，Axios 的拦截器体系更顺手。

## 常见追问

### Q: 你做技术选型的时候，最看重什么？

**回答要点：**
- 不说"最看重性能"，要说"最看重是否匹配团队和业务"
- 性能差异在大部分业务场景下感知不大，但团队熟悉度直接影响交付速度和质量
- 社区活跃度很重要 — 遇到问题能搜到解决方案，有持续维护

### Q: 选了一个技术后来发现不合适，怎么办？

**回答要点：**
1. **先评估影响** — 不合适到什么程度？是"用着别扭"还是"严重阻碍开发"？
2. **探索补救方案** — 能不能通过封装、插件、配置来弥补？
3. **制定迁移计划** — 如果确定要换，渐进式迁移（新功能用新技术，老功能逐步重构）
4. **记录教训** — 为什么当初选错了？是信息不全还是判断失误？下次怎么避免？

### Q: 你会选择最新的技术还是成熟的技术？

**回答要点：**
- 取决于项目性质和团队风险承受能力
- **核心业务**：选成熟稳定的，不能拿生产环境当试验田
- **创新项目/内部工具**：可以尝试新技术，试错成本低
- **判断标准**：看这个技术是"有潜力但未成熟"还是"已经死了"。比如 Vue 3 刚发布时不算成熟但方向明确，可以跟进；某些小众框架就不值得赌

## 可用案例

### 案例：贷后自助服务平台的技术选型

| 决策 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（React） | 需要 SSR，React 生态成熟 |
| UI 库 | shadcn/ui + Tailwind | 需要高度定制，shadcn/ui 可以 copy 出源码修改 |
| 后端 | NestJS | 需要装饰器体系做统一鉴权，TypeScript 原生支持 |
| ORM | Prisma | 类型安全、Migration 管理、开发效率高 |
| 数据库 | SQLite → PostgreSQL | 初期数据量小，SQLite 零配置；后续数据增长后迁移 |
| 缓存 | Redis | 热门接口缓存，QPS 从 200 提升到 1200 |

## 回答要点总结

1. 技术选型没有标准答案，关键是**决策过程是否合理**
2. 每个选择都要能说清楚"为什么选 A 不选 B"
3. 要体现 trade-off 思维 — 没有完美方案，只有最适合的方案
4. 结合自己的项目案例，用具体数据支撑选择的合理性
