# 0-1 架构设计方法论

## 核心概念

### 0-1 架构设计的关键阶段

```
需求分析 → 技术选型 → 架构设计 → 骨架搭建 → 迭代演进
    ↑                                        ↓
    ←←←←←←←← 反馈调整 ←←←←←←←←←←←←←←←←←←←←←
```

1. **需求分析** — 明确业务边界、用户场景、性能要求、团队能力
2. **技术选型** — 基于需求和团队情况选择技术栈
3. **架构设计** — 模块划分、数据流设计、状态管理方案
4. **骨架搭建** — 项目初始化、目录结构、基础组件、CI/CD
5. **迭代演进** — 根据业务发展逐步优化架构

### 前端 0-1 架构设计的核心决策点

| 决策点 | 考虑因素 | 示例 |
|---|---|---|
| 框架选择 | 团队熟悉度、生态、性能需求、招聘难度 | React vs Vue vs Angular |
| 构建工具 | 开发体验、构建速度、生态插件 | Vite vs Webpack vs Rspack |
| 状态管理 | 应用复杂度、数据流方向、团队理解成本 | Redux vs Zustand vs Context |
| 路由方案 | SSR 需求、权限粒度、代码分割 | React Router vs Next.js Router |
| UI 组件库 | 定制需求、设计规范、社区活跃度 | Ant Design vs 自建 |
| 接口层 | 类型安全、缓存策略、错误处理 | Axios vs SWR vs React Query |
| 部署方案 | CDN、SSR、容器化、灰度发布 | Vercel vs K8s vs 传统部署 |

### 架构设计的核心原则

1. **渐进式架构** — 不要一开始就设计一个完美架构，先满足当前需求，保留演进空间
2. **约定大于配置** — 统一目录结构、命名规范、文件组织方式，减少决策成本
3. **关注点分离** — 业务逻辑、UI 渲染、数据获取、状态管理各层解耦
4. **可测试性** — 架构设计时就要考虑单元测试怎么写，纯函数优先
5. **性能预算** — 从第一天就设定性能指标（JS bundle 大小、首屏时间、交互响应时间）

### 目录结构设计（以 React 项目为例）

```
src/
├── app/              # 路由页面（Next.js App Router 风格）
├── components/       # 通用组件
│   ├── ui/           # 基础 UI 组件（Button, Input...）
│   └── biz/          # 业务组件
├── hooks/            # 自定义 Hooks
├── lib/              # 工具函数和第三方封装
├── services/         # 接口请求层
├── stores/           # 状态管理
├── types/            # 全局类型定义
├── constants/        # 常量
└── styles/           # 全局样式
```

## 常见追问

### Q: 你主导过 0-1 的项目吗？说说你的技术选型思路

**回答框架：**
1. **先搞清楚需求** — 项目给谁用、什么场景、有多少用户、性能要求
2. **评估团队情况** — 团队几个人、技术背景、学习成本
3. **列出候选方案** — 每个技术选型至少列出 2-3 个候选
4. **对比关键维度** — 性能、生态、社区活跃度、长期维护性、招聘难度
5. **做出决策并说明理由** — 选了什么、为什么选、放弃了什么、为什么放弃

**示例（贷后自助服务平台）：**
- 选 Next.js 而不是纯 CSR：因为 C 端需要 SEO 和首屏性能
- 选 NestJS 而不是 Express：因为需要装饰器 + Guard 体系做统一鉴权
- 选 Prisma 而不用原生 SQL：因为类型安全和开发效率
- 选 SQLite 而不是 PostgreSQL：因为初期数据量小，部署简单，后期可迁移

### Q: 架构设计中最容易犯的错误是什么？

**回答要点：**
1. **过度设计** — 一开始就设计一个"万能架构"，结果大部分能力用不上
2. **技术选型跟风** — 选最新的技术而不是最适合的
3. **忽略团队能力** — 架构再好，团队不理解也落地不了
4. **没有演进计划** — 架构不是一成不变的，要有从 MVP 到成熟的演进路径
5. **忽略非功能需求** — 只考虑功能实现，不考虑性能、安全、可维护性

### Q: 怎么评估一个架构方案的好坏？

**回答要点：**
1. **可维护性** — 新人能否在 1-2 周内上手并独立开发
2. **可扩展性** — 新增一个功能模块需要改动多少现有代码
3. **性能** — 是否满足性能预算（首屏时间、交互响应、内存占用）
4. **稳定性** — 错误处理是否完善、是否有监控兜底
5. **开发效率** — 日常开发体验如何（热更新速度、类型提示、调试便利性）

## 可用案例

### 案例 1：贷后自助服务平台（全栈 0-1）
- **决策过程**：Next.js SSR + NestJS API + Prisma ORM
- **关键权衡**：SSR vs CSR、SQLite vs PostgreSQL、shadcn/ui vs Ant Design
- **踩坑**：Next.js App Router 的缓存机制、Prisma 的 N+1 问题

### 案例 2：智能客服平台微前端改造
- **决策过程**：单体 → 微前端的渐进式演进
- **关键权衡**：qiankun vs iframe vs Module Federation
- **踩坑**：样式隔离、全局状态共享、子应用通信

## 回答要点总结

1. 强调"渐进式"思维 — 不追求一步到位
2. 每个决策要有 trade-off 分析 — 不是"选了最好的"，而是"选了最合适的"
3. 结合具体项目案例 — 用贷后自助服务平台或智能客服平台举例
4. 考虑团队因素 — 架构是给团队用的，不是给自己炫技的
