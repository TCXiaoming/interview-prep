# AI 前沿技术（面试向）

## 基础概念

### LLM（大语言模型）

Large Language Model，基于 Transformer 架构的大规模预训练语言模型。通过海量文本数据学习语言模式，能生成、理解、推理文本。

### Token

LLM 处理文本的最小单位。不等于一个字或一个词。

- 英文：约 1 token ≈ 4 个字符 ≈ 0.75 个单词
- 中文：约 1-2 个汉字 = 1 token
- 特殊符号单独计为 1 token

**实际影响：** 计费、上下文窗口限制、响应速度都和 token 数直接相关。

### Context Window（上下文窗口）

模型一次能处理的最大 token 数（输入 + 输出）。

| 模型 | 上下文窗口 |
|---|---|
| GPT-3.5 | 4K / 16K |
| GPT-4 | 8K / 32K / 128K |
| Claude 3 | 200K |
| Gemini 1.5 | 1M |

超长上下文会导致"大海捞针"问题 — 模型可能忽略中间的信息（Lost in the Middle）。

### Temperature（温度参数）

控制生成文本的随机性，范围通常 0-2。

- **0** — 最确定，每次输出几乎一样（适合代码生成、事实回答）
- **0.7** — 平衡创造性和准确性（通用对话）
- **1.0+** — 高随机性，更有创意但可能胡说八道（诗歌、创意写作）

**原理：** Temperature 影响 softmax 的概率分布。值越大，概率分布越平坦，低概率词被选中的机会增加。

### Hallucination（幻觉）

模型生成的内容看起来合理但实际上是错误的或编造的。

**类型：**
- **事实性幻觉** — 编造不存在的事实（如引用不存在的论文）
- **忠实性幻觉** — 回答和提供的上下文不一致
- **指令幻觉** — 没有按照指令要求回答

**缓解方法：** RAG（检索增强生成）、要求模型引用来源、降低 Temperature、限定回答范围。

## 核心技术

### Embedding（向量化）

将文本转化为高维向量（如 1536 维），使语义相似的文本在向量空间中距离接近。

```
"猫" → [0.12, -0.34, 0.56, ...]
"小猫" → [0.11, -0.33, 0.55, ...]  // 语义相近，向量也相近
"飞机" → [0.78, 0.23, -0.45, ...]  // 语义远，向量也远
```

**用途：** 语义搜索、聚类、分类、推荐系统。

### 向量数据库

专门存储和检索高维向量的数据库。

| 数据库 | 特点 |
|---|---|
| Pinecone | 全托管，简单易用 |
| Milvus | 开源，高性能，大厂常用 |
| Chroma | 轻量，适合原型开发 |
| Weaviate | 支持混合搜索 |
| pgvector | PostgreSQL 插件，已有 PG 生态可复用 |

**核心能力：** 相似度搜索（余弦相似度、欧氏距离、内积）。

### 语义相似度

衡量两段文本在含义上的相似程度，通常用向量间的余弦相似度计算：

```python
cosine_similarity = dot(A, B) / (||A|| * ||B||)
# 范围 [-1, 1]，1 表示完全相似
```

和关键词匹配的区别：语义相似度理解"意思"，"猫"和"小猫"语义相似但关键词不同。

## 进阶概念

### RAG（检索增强生成）

Retrieval-Augmented Generation。先检索相关文档，再将文档作为上下文给 LLM 生成回答。

```
用户提问 → Embedding → 向量数据库检索相关文档 → 将文档 + 问题一起给 LLM → LLM 基于文档回答
```

**优势：**
- 解决幻觉 — LLM 的回答基于真实文档，不是凭空编造
- 知识可更新 — 更新文档库就行，不需要重新训练模型
- 可溯源 — 能告诉用户答案来自哪个文档

**挑战：**
- 检索质量决定回答质量（garbage in, garbage out）
- 文档切分策略影响检索效果
- 长文档需要合理的 chunking 策略

### Fine-tuning（微调）

用特定领域的数据继续训练预训练模型，让模型更适应特定任务。

**与 RAG 的对比：**
| 维度 | Fine-tuning | RAG |
|---|---|---|
| 目的 | 教模型新知识/风格 | 给模型外部知识 |
| 成本 | 高（需要 GPU 训练） | 低（只需向量数据库） |
| 知识更新 | 需要重新训练 | 更新文档即可 |
| 适用场景 | 特定领域格式、风格 | 知识问答、文档检索 |

### Prompt Engineering（提示工程）

通过设计提示词来引导 LLM 输出期望结果的技术。

**核心技巧：**
1. **System Prompt** — 设定角色和行为规范
2. **Few-shot Learning** — 给几个示例，模型学会格式
3. **Chain of Thought（CoT）** — 要求模型"一步步思考"
4. **结构化输出** — 要求 JSON/Markdown 等特定格式

### Few-shot vs Zero-shot

| 类型 | 说明 | 示例 |
|---|---|---|
| Zero-shot | 不给示例，直接提问 | "把这句话翻译成英文" |
| Few-shot | 给 1-5 个示例 | "猫→cat，狗→dog，鱼→?" |
| One-shot | 只给 1 个示例 | Few-shot 的特殊情况 |

### Chain of Thought（CoT，思维链）

要求模型展示推理过程，而不是直接给答案。

```
# 没有 CoT
Q: 一个班 30 人，男生比女生多 6 人，女生多少人？
A: 12（可能错）

# 有 CoT
Q: ...请一步步推理。
A: 设女生 x 人，男生 x+6 人。
   x + (x+6) = 30
   2x = 24
   x = 12
   A: 女生 12 人（正确）
```

### Function Calling

让 LLM 结构化地调用外部工具/API 的能力。

```json
// LLM 返回的不是自然语言，而是结构化的函数调用
{
  "name": "get_weather",
  "arguments": { "city": "北京" }
}
```

**用途：** 让 LLM 能查天气、查数据库、发邮件、执行代码等。

### Agent（AI 智能体）

能自主规划、使用工具、完成多步骤任务的 AI 系统。

```
用户目标 → Agent 理解意图 → 规划步骤 → 选择工具执行 → 观察结果 → 决定下一步 → ... → 完成
```

**核心能力：**
- **规划** — 将复杂任务拆解为子任务
- **工具使用** — 调用 API、执行代码、搜索网络
- **记忆** — 短期记忆（上下文）和长期记忆（向量数据库）
- **反思** — 评估执行结果，必要时调整策略

### ReAct 范式

Reasoning + Acting，Agent 的一种实现范式。

```
Thought: 我需要查一下北京的天气
Action: get_weather(city="北京")
Observation: 晴，25°C
Thought: 用户需要知道穿什么，根据天气给出建议
Final Answer: 北京今天晴天，25°C，建议穿短袖。
```

**与纯 LLM 调用的区别：**
- 纯 LLM 调用：输入 → 模型 → 输出（单步）
- Agent：输入 → 模型思考 → 调用工具 → 获取结果 → 再思考 → ...（多步循环）

### Multi-Agent System（多智能体系统）

多个 Agent 协作完成任务，每个 Agent 负责不同的角色/专长。

```
用户需求 → 路由 Agent → 分配给专业 Agent
                          ├── 代码 Agent（写代码）
                          ├── 测试 Agent（写测试）
                          └── 文档 Agent（写文档）
                         ← 汇总结果 → 用户
```

**示例框架：** AutoGen、CrewAI、LangGraph。

### Plan-and-Solve

先让模型制定计划，再逐步执行。比直接回答更可靠，特别是复杂任务。

```
# 第一步：制定计划
Plan:
1. 分析需求
2. 设计方案
3. 实现代码
4. 编写测试

# 第二步：逐步执行
Step 1: ...
Step 2: ...
```

## 前沿技术与前端的关系

### AI 对前端开发的影响

1. **AI 生成 UI** — v0、Bolt 等工具能根据描述生成 UI 代码
2. **AI 辅助编码** — Copilot、Cursor 提升编码效率
3. **AI 对话界面** — ChatBot UI 成为新的常见交互模式（流式渲染、Markdown 渲染）
4. **RAG 应用** — 知识库问答、文档搜索等前端产品

### 前端工程师需要了解的 AI 能力

1. **SSE（Server-Sent Events）** — AI 流式输出的基础
2. **Markdown 渲染** — `react-markdown`、`marked` 处理 AI 输出
3. **代码高亮** — `shiki`、`prismjs` 渲染 AI 生成的代码块
4. **Token 计数** — 控制上下文长度，避免超限
5. **向量搜索** — 在前端做简单的语义搜索（调用 Embedding API）

## 常见追问

### Q: RAG 和微调怎么选？

**回答要点：**
- 如果是给模型补充外部知识 → RAG
- 如果是让模型适应特定格式/风格 → 微调
- 大部分场景 RAG 就够了，成本低、效果好、可维护
- 两者可以结合：先微调让模型适应领域，再用 RAG 补充最新知识

### Q: 怎么减少 AI 的幻觉？

**回答要点：**
1. RAG — 给模型真实文档作为上下文
2. 要求引用来源 — "根据第 X 段文档..."
3. 限定回答范围 — "只根据提供的文档回答，不知道就说不知道"
4. 降低 Temperature — 减少随机性
5. 多步验证 — 用第二个模型验证第一个模型的回答

### Q: 你觉得 AI 会怎么改变大疆的产品？

**回答要点（开放题）：**
- **飞行控制** — AI 辅助避障、自动跟踪、智能航拍
- **影像处理** — AI 增强画质、自动剪辑、智能美颜
- **用户体验** — AI 驱动的智能助手、自然语言操控无人机
- **数据服务** — 农业无人机的数据分析、测绘数据处理
- **前端层面** — 更智能的控制界面、AI 生成的飞行路线预览、实时数据可视化
