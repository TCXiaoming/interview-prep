# 场景题（面试高频）

## 场景 1：从输入 URL 到页面展示

### 完整流程

```
1. URL 解析
   → 判断是搜索关键词还是 URL
   → URL 补全（加 https://）

2. DNS 解析（递归 + 迭代）
   → 浏览器缓存 → OS 缓存 → hosts 文件
   → 本地 DNS 服务器 → 根域名服务器 → 顶级域名服务器 → 权威域名服务器
   → 得到 IP 地址

3. TCP 连接
   → 三次握手（SYN → SYN+ACK → ACK）
   → 如果是 HTTPS：TLS 握手（TLS 1.2: 2-RTT, TLS 1.3: 1-RTT）

4. 发送 HTTP 请求
   → 请求行（方法、URL、协议版本）
   → 请求头（Host、Cookie、Accept、User-Agent...）
   → 请求体（POST/PUT 的数据）

5. 服务端处理
   → 负载均衡 → 应用服务器 → 处理请求 → 返回响应

6. 接收 HTTP 响应
   → 状态行（状态码）
   → 响应头（Content-Type、Cache-Control、Set-Cookie...）
   → 响应体

7. 浏览器解析渲染
   → HTML 解析 → DOM Tree
   → CSS 解析 → CSSOM
   → DOM + CSSOM → Render Tree
   → Layout（计算位置大小）
   → Paint（绘制图层）
   → Composite（合成，GPU 加速）
   → JS 执行（可能阻塞解析）

8. 连接管理
   → HTTP/1.1: Keep-Alive 保持连接
   → HTTP/2: 多路复用
   → 关闭时四次挥手
```

### 深入追问

**Q: DNS 解析用的是什么协议？**
UDP（端口 53）。因为 DNS 查询数据量小、不需要可靠性保证，UDP 更快。但区域传输（AXFR）用 TCP。

**Q: 为什么需要三次握手而不是两次？**
防止历史连接浪费资源 + 确保双方的初始序列号都被确认。

**Q: 浏览器解析遇到 `<script>` 标签会怎样？**
默认会阻塞 HTML 解析，等 JS 下载并执行完再继续。`defer` 不阻塞解析、DOM 解析完后执行；`async` 下载完就执行、不保证顺序。

## 场景 2：如何确保代码的可维护性

### 回答框架

1. **规范层** — ESLint + Prettier + TypeScript strict mode
2. **架构层** — 模块化、组件化、关注点分离
3. **文档层** — 类型即文档、README、API 文档
4. **质量层** — Code Review + 单元测试 + CI/CD
5. **监控层** — Sentry 错误监控 + 性能监控

```ts
// 1. TypeScript 严格模式

// 2. 清晰的目录结构
src/
  components/   # 通用组件
  features/     # 按业务领域组织
  hooks/        # 自定义 hooks
  services/     # API 层

// 变量/函数：camelCase
// 组件/类型：PascalCase
// 常量：UPPER_SNAKE_CASE
// 文件：kebab-case（或 PascalCase，团队统一）

// 4. Code Review 清单
// - 是否有潜在的空值问题
// - 错误处理是否完善
// - 是否有内存泄漏风险
// - 是否遵循团队规范
```

## 场景 3：CDN 能部署 SPA 吗？

**可以，但需要特殊配置。**

SPA 使用前端路由（history 模式），所有路径都应返回 `index.html`。

```nginx
# Nginx 配置
location / {
  try_files $uri $uri/ /index.html;
}
```

**CDN 配置：**
1. 所有静态资源（JS/CSS/图片）→ 正常 CDN 缓存
2. HTML 文件 → 不缓存或短时间缓存（`Cache-Control: no-cache`）
3. 配置错误页面 → 404 返回 `index.html`（让前端路由处理）

**Hash 模式不需要特殊配置** — 因为 URL 中 `#` 后面的部分不会发给服务器。

## 场景 4：React 和 Vue 的技术层面区别

| 维度 | React | Vue |
|---|---|---|
| 响应式 | 不是响应式的，需要 setState 触发重渲染 | 响应式系统自动追踪依赖 |
| 更新粒度 | 组件级（整个组件重渲染） | 精确到具体 DOM 节点 |
| JSX vs 模板 | JSX（JS 中写 HTML） | 模板语法（HTML 为主） |
| 状态管理 | 推荐外部库（Redux/Zustand） | 内置（Pinia/Vuex） |
| 编译优化 | 运行时 diff（不区分静态/动态） | 编译时标记 Patch Flags，diff 跳过静态节点 |
| Fiber | 有（可中断渲染） | 无（同步 diff，但 Diff 本身快） |
| 学习曲线 | 偏陡（Hooks 思维、不可变更新） | 偏平缓（模板直观、响应式自动） |

**核心差异总结：** React 是"手动挡"——你需要告诉它什么时候更新（setState/useState），更新时重渲染整个组件子树。Vue 是"自动挡"——响应式系统自动追踪依赖，精确更新变化的部分。

## 场景 5：如何引入新技术/工具的决策过程

### 回答框架（STAR + 决策矩阵）

1. **识别痛点** — 当前方案有什么问题？（效率低、性能差、难维护）
2. **调研候选方案** — 列出 2-3 个备选
3. **多维度评估** — 功能、性能、学习成本、社区、长期维护性
4. **小范围试点** — 在非核心模块先试用，验证效果
5. **数据驱动决策** — 用数据证明效果（如构建速度、bug 率、开发效率）
6. **渐进式推广** — 试点成功后推广到全团队

**示例：** 引入 Sentry 前端监控
- 痛点：线上错误靠用户反馈，定位慢
- 候选：Sentry vs 自建 vs Fundebug
- 评估：Sentry 社区最大、支持 SourceMap、和团队技术栈兼容
- 试点：先接入一个子应用，收集 2 周数据
- 效果：错误发现时间从天级降到分钟级
- 推广：所有应用接入

## 场景 6：HTTPS 密钥交换原理

**核心问题：** 如何在不安全的信道上安全地协商密钥？

### TLS 1.2 密钥交换

```
Client                              Server
  |--- Client Hello (支持的算法) --->|
  |<-- Server Hello (选定算法) ------|
  |<-- Certificate (服务端证书) ------|
  |<-- Server Key Exchange ---------|
  |                                   |
  | 客户端验证证书（CA 链验证）         |
  | 客户端生成预主密钥                  |
  | 用服务端公钥加密预主密钥            |
  |--- Client Key Exchange --------->|
  |                                   |
  | 双方用预主密钥生成会话密钥          |
  |--- Change Cipher Spec ---------->|
  |--- Finished -------------------->|
  |<-- Change Cipher Spec -----------|
  |<-- Finished ---------------------|
  |======== 对称加密通信 ============|
```

### TLS 1.3 改进

- 只支持 ECDHE（椭圆曲线 Diffie-Hellman 前向安全密钥交换）
- 握手从 2-RTT 降到 1-RTT
- 支持 0-RTT（恢复会话时）
- 移除不安全算法（RSA 密钥交换、CBC 模式、SHA-1）

### ECDHE 密钥交换

```
客户端：生成随机数 a，计算 A = a * G（椭圆曲线点）
服务端：生成随机数 b，计算 B = b * G
双方交换 A 和 B
客户端：共享密钥 = a * B = a * b * G
服务端：共享密钥 = b * A = b * a * G
→ 双方得到相同的共享密钥，中间人即使截获 A 和 B 也无法推算密钥
```

## 场景 7：如何管理和优化前端依赖项

### 依赖管理

1. **版本锁定** — `package-lock.json` / `pnpm-lock.yaml` 锁定精确版本
2. **定期审计** — `npm audit` / `snyk` 检查安全漏洞
3. **清理无用依赖** — `depcheck` 检测未使用的依赖
4. **幽灵依赖治理** — 所有依赖显式声明，用 pnpm 严格模式

### 依赖优化

1. **按需引入** — `import { Button } from 'antd'` 而不是 `import antd`
2. **替换大依赖** — moment → dayjs，lodash → lodash-es
3. **CDN 外链** — 稳定大依赖（React/Vue）用 CDN 引入
4. **Tree Shaking** — 确保用 ESM 模块、标记 `sideEffects: false`
5. **分析包体积** — `webpack-bundle-analyzer` / `vite-plugin-visualizer`

## 场景 9：前端模块化 vs 组件化

| 维度 | 模块化 | 组件化 |
|---|---|---|
| 关注点 | 代码组织和复用 | UI 和交互的封装 |
| 单位 | JS 模块（函数、类、对象） | UI 组件（模板 + 逻辑 + 样式） |
| 工具 | ES Module、CommonJS | React Component、Vue SFC |
| 复用方式 | import/export | props/slots/scope |
| 边界 | 逻辑边界 | UI 边界 |

两者不冲突 — 组件内部使用模块化组织代码，组件本身是 UI 复用的单元。

## 场景 10：ES 模块转 CommonJS 的最大难点

**核心问题：** ESM 是静态的（编译时确定依赖），CJS 是动态的（运行时 require）。

| 差异 | ESM | CJS |
|---|---|---|
| 加载时机 | 编译时（静态） | 运行时（动态） |
| 导出 | `export`（绑定引用） | `module.exports`（值拷贝） |
| 循环引用 | 支持（导出的是引用） | 部分支持（可能拿到未初始化的值） |
| 动态导入 | `import()` | `require()` 天然动态 |
| Top-level await | 支持 | 不支持 |

**最难的部分：** ESM 的 `export` 导出的是实时绑定（live binding），值会随源模块变化。CJS 的 `module.exports` 是值拷贝，导出后源模块变化不会反映。

```js
// ESM — 导出的是引用
// counter.mjs
export let count = 0;
export function increment() { count++; }

// main.mjs
import { count, increment } from './counter.mjs';
console.log(count); // 0
increment();
console.log(count); // 1 ← count 自动更新

// 转为 CJS 后 — 导出的是值拷贝
// count 拿到的是 0 的副本，increment 后不会变
```

**解决：** 用 getter 导出或用对象引用代替基本类型。
