# Fiber 架构

## 核心概念

React 16 引入的新协调引擎，将原来同步不可中断的递归 diff 改为**可中断、可恢复的异步计算**。

**数据结构改变**：每个 Fiber 节点是一个对象，包含三个关键指针：
- `child`：第一个子节点
- `sibling`：下一个兄弟节点
- `return`：父节点

用链表 + 循环替代了原来的树 + 递归，遍历可以在任意节点暂停，下次从断点继续。

**两个阶段**：
- **Render 阶段**（可中断）：遍历 Fiber 树，计算变更，纯内存操作
- **Commit 阶段**（不可中断）：将变更一次性应用到真实 DOM

**Commit 阶段的三个子阶段：**
1. **before mutation** — 读取 DOM 状态快照，执行 `getSnapshotBeforeUpdate`（类组件）
2. **mutation** — 将变更应用到真实 DOM（增删改节点），此时 DOM 已更新但浏览器**尚未绘制**
3. **layout** — DOM 已更新、浏览器仍未绘制，执行 `useLayoutEffect` 和 `componentDidMount/Update`

`useEffect` 不在 Commit 阶段执行，而是在浏览器绘制完成后**异步调度**（通过 Scheduler 的 idle 回调或宏任务）。所以：
- `useLayoutEffect` → 同步，在 layout 阶段执行，**阻塞浏览器绘制**
- `useEffect` → 异步，在浏览器绘制后执行，**不阻塞绘制**

```
Render(可中断) → Commit(不可中断) → 浏览器绘制
  (diff)         before mutation
                 mutation(DOM更新)
                 layout(useLayoutEffect)
                                    → 绘制完成 → useEffect
```

**调度机制**：React 自实现了 scheduler，利用 `MessageChannel` 模拟时间切片，在每帧空闲时间执行 Render 阶段工作，超时则暂停让出主线程。

## 常见追问

- Fiber 节点上存了哪些信息？
- Render 阶段和 Commit 阶段分别做什么？
- 为什么 Commit 阶段不能中断？
- React 用的是 requestIdleCallback 吗？

## 回答要点

**为什么不用 requestIdleCallback**：兼容性差，且触发频率不稳定，React 用 `MessageChannel` 自己实现了一套优先级调度。

**Commit 阶段不可中断**：因为涉及真实 DOM 操作，中断会导致 UI 不一致，用户看到半更新的界面。

**可中断的本质**：不依赖调用栈（递归），而是用显式的指针记录"当前处理到哪"，随时可以保存现场、恢复执行。
