# Vue 状态管理

## 核心概念

### 状态管理的演进

```
Vue 2 options API          Vue 3 Composition API
  data/computed/watch        ref/reactive/computed
        ↓                            ↓
  Vuex (v3/v4)              Pinia (Vue 3 官方推荐)
   centralized store         modular stores
```

### Pinia 核心概念

**定义 Store：**
```js
import { defineStore } from 'pinia'

export const useCounterStore = defineStore('counter', () => {
  // state — 用 ref/reactive
  const count = ref(0)
  const name = ref('counter')

  // getters — 用 computed
  const doubleCount = computed(() => count.value * 2)

  // actions — 普通函数
  function increment() {
    count.value++
  }

  return { count, name, doubleCount, increment }
})
```

**在组件中使用：**
```vue
<script setup>
const store = useCounterStore()

// ✅ 直接解构（用 storeToRefs 保持响应式）
const { count, doubleCount } = storeToRefs(store)
const { increment } = store  // actions 可以直接解构
</script>
```

### Pinia vs Vuex 对比

| | Vuex | Pinia |
|---|---|---|
| API 风格 | Options API（mutations/actions 分离） | Composition API（setup store） |
| TypeScript | 不友好，需要大量类型定义 | 原生支持，类型推导好 |
| mutations | 必须有（同步修改 state） | 无 mutations，直接修改 state |
| 模块 | `modules: {}` 嵌套，命名空间需手动配置 | 独立 defineStore，天然隔离 |
| DevTools | 支持 | 支持，更简洁 |
| 体积 | ~9KB | ~1KB |

## 常见追问

### Q: Pinia 为什么去掉了 mutations？

**回答要点：**

Vuex 的 mutations 是为了 DevTools 能追踪每次 state 变更而设计的约束。但实际开发中：
1. **actions 里直接修改 state 是常见模式** — 大量模板代码是 actions 调 mutations，mutations 再改 state
2. **Vue DevTools 已经能追踪 ref/reactive 的变化** — 不需要强制 mutations 也能记录变更历史
3. **Composition API 的灵活性** — 用 setup store 可以直接操作 ref，mutations 变成多余约束

```js
// Vuex — 模板代码多
actions: {
  increment(ctx) {
    ctx.commit('INCREMENT') // 必须通过 mutation
  }
},
mutations: {
  INCREMENT(state) { state.count++ }
}

// Pinia — 直接
actions: {
  increment() {
    this.count++  // 直接改，DevTools 依然能追踪
  }
}
```

### Q: Pinia 的 store 之间如何通信？

**回答要点：**

直接互相引用即可，不需要任何事件总线：

```js
// stores/user.js
export const useUserStore = defineStore('user', () => {
  const token = ref('')
  return { token }
})

// stores/cart.js
import { useUserStore } from './user'

export const useCartStore = defineStore('cart', () => {
  const userStore = useUserStore()
  const items = ref([])

  const checkout = async () => {
    // 直接引用另一个 store 的状态
    const res = await api.checkout(userStore.token, items.value)
  }

  return { items, checkout }
})
```

**原理**：Pinia 的 store 是单例的（useXxxStore 返回同一个实例），所以引用另一个 store 就是引用同一个响应式对象。

### Q: Vue 项目中怎么选状态管理方案？

**回答要点：**

| 项目规模 | 方案 | 理由 |
|---------|------|------|
| 小型（1-3 个页面） | 不引入，只用 provide/inject | 状态简单，pinia/vuex 过重 |
| 中型（多个页面共享状态） | Pinia | 官方推荐，TS 友好，轻量 |
| 大型（微前端/复杂状态流） | Pinia + 分层 | 多个 store 按领域拆分 |
| 需要持久化存储 | Pinia + pinia-plugin-persistedstate | 开箱即用 |

**provide/inject 的适用场景：**
```vue
<!-- 主题、用户信息等全局只读状态 -->
<script setup>
const theme = ref('light')
provide('theme', theme)
provide('setTheme', (t) => { theme.value = t })
</script>
```

**什么时候需要 Pinia：**
- 多个不相关的组件共享同一份状态（跨层级、跨路由）
- 状态有复杂的异步操作和组合逻辑
- 需要 DevTools 调试状态变更历史

### Q: 为什么 Vue 3 推荐 Composition API + provide/inject 替代 EventBus？

**回答要点：**

1. **响应式丢失** — EventBus 传递的是普通值，不是响应式对象
2. **难以追踪** — EventBus 的事件发射和监听是分离的，代码量大了不知道谁发了什么事件
3. **内存泄漏** — 组件销毁时容易忘记 `$off`
4. **TypeScript 不友好** — 事件名和参数类型无法推导

```js
// ❌ EventBus（Vue 2 常见模式）
const bus = new Vue()
bus.$emit('update', data)
bus.$on('update', handler) // 谁发的？什么数据？查起来麻烦

// ✅ provide/inject（Vue 3 推荐）
// 父组件提供，子组件注入，天然响应式，TS 友好
```

### Q: SSR 场景下状态管理要注意什么？

**回答要点：**

核心问题：**SSR 服务端和客户端共享同一个 store 实例会导致状态污染**。

```js
// ❌ 错误：模块级单例
const store = createPinia()
app.use(store) // 服务端所有请求共享同一个 store，请求 A 的数据会泄露给请求 B

// ✅ 正确：每次请求创建新实例
export function createApp() {
  const store = createPinia()
  const app = createSSRApp(App)
  app.use(store)
  return { app, store }
}

// 服务端入口：每个请求都调 createApp
export async function render(url) {
  const { app, store } = createApp()
  // 填充数据到 store
  await store.state.xxx
  // 渲染 HTML + 注入 store.state 到 window.__INITIAL_STATE__
}
```

**关键做法**：
- 每个请求创建独立的 store 实例
- 服务端渲染时填充 store 数据
- 将服务端 store 状态序列化到 HTML 的 `__INITIAL_STATE__` 中
- 客户端 hydration 时用 `__INITIAL_STATE__` 初始化 store（`createPinia().state`）
