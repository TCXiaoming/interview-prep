# ref 与 reactive

## 核心概念

两者都创建响应式数据，区别在于适用类型和使用方式：

| <br /> | ref                   | reactive |
| ------ | --------------------- | -------- |
| 适用类型   | 基本类型 + 对象             | 仅对象（含数组） |
| 访问方式   | JS 中需 `.value`，模板自动解包 | 直接访问     |
| 返回值    | RefImpl 对象            | Proxy 对象 |

## ref 内部实现

```js
function ref(value) {
  return {
    get value() {
      track(this, 'value') // 收集依赖
      return this._value
    },
    set value(newVal) {
      this._value = newVal
      trigger(this, 'value') // 触发更新
    },
    _value: isObject(value) ? reactive(value) : value // 对象走 reactive
  }
}
```

**关键点**：ref 传入对象时，内部会调用 `reactive` 处理，所以 `ref({a:1}).value` 和 `reactive({a:1})` 的响应式机制完全一样，只是多了一层 `.value` 包装。

## 常见追问

### Q: 为什么 ref 在模板里不需要 .value？

**回答要点：**

Vue 3 编译器在编译模板时，会自动检测 ref 对象并加上 `.value`。这是编译时优化：

```vue
<template>
  <div>{{ count }}</div>
</template>

<script setup>
const count = ref(0)
</script>
```

编译后相当于：`<div>{{ count.value }}</div>`

编译器通过检测变量是否为 RefImpl 实例来决定是否解包。只有**顶层 ref 属性**会解包，嵌套在 reactive 或普通对象中的 ref 在某些场景不会自动解包。

### Q: toRef 和 toRefs 是干什么的？

**回答要点：**

两者都用于保持响应式引用，区别在于作用范围：

- **toRef**：将 reactive 对象的**单个属性**转为独立的 ref
- **toRefs**：将 reactive 对象的**所有属性**转为 ref 对象

```js
const state = reactive({ count: 0, name: 'vue' })

// toRef — 单个属性
const countRef = toRef(state, 'count')
countRef.value++ // 修改 ref 会触发 state.count 的更新

// toRefs — 全部属性，常用于解构
const { count, name } = toRefs(state)
count.value++ // 解构后保持响应式
```

**核心原理**：toRef 创建的 ref 和原始 reactive 属性维持了引用关系，本质上是对同一个 Proxy 属性的引用，所以修改 ref 会触发原始对象的更新。

### Q: 解构后响应式会丢失吗？

**回答要点：**

| 方式                      | 是否丢失 | 原因                        |
| ----------------------- | ---- | ------------------------- |
| `reactive()` 解构         | ❌ 丢失 | 解构拿到的是普通值，与 Proxy 的引用断开   |
| `ref()` 解构              | ❌ 丢失 | 解构拿到的是 `.value` 的副本       |
| `toRefs(reactive())` 解构 | ✅ 保持 | 每个属性转为 ref，与原始 Proxy 保持关联 |

```js
const state = reactive({ count: 0, name: 'vue' })

// ❌ 丢失响应式
let { count } = state // count 是 0（普通数值），不再响应
count++ // state.count 还是 0

// ✅ 保持响应式
const { count } = toRefs(state)
count.value++ // state.count 变成了 1
```

### Q: shallowRef 和 shallowReactive 是什么？和 ref/reactive 有什么区别？

**回答要点：**

| API               | 响应式深度                 | 场景        |
| ----------------- | --------------------- | --------- |
| `ref`             | 深层（对象内部走 reactive）    | 默认选择      |
| `shallowRef`      | 仅 `.value` 层面，**不递归** | 大对象、不可变数据 |
| `reactive`        | 深层（递归 Proxy）          | 对象状态管理    |
| `shallowReactive` | 仅第一层属性                | 性能敏感场景    |

```js
// shallowRef — 只追踪 .value 的变化
const obj = shallowRef({ a: { b: 1 } })
obj.value.a.b = 2    // ❌ 不会触发更新（内部没有 Proxy 代理）
obj.value = { a: { b: 2 } }  // ✅ 触发更新（.value 被替换）

// 适用场景：和 immer 配合做不可变数据
const state = shallowRef(initialData)
state.value = produce(state.value, draft => {
  draft.items.push(newItem)  // immer 返回新对象，shallowRef 检测到 .value 变化
})
```

**性能差异**：深层响应式要递归代理整个对象。对于大型列表或复杂嵌套数据结构，shallowRef 在修改和访问时性能好得多——但你得自己保证变更方式是可触发响应式的（替换整个 `.value` 而非修改内部属性）。

### Q: reactive 为什么不能直接重新赋值？

**回答要点：**

`reactive()` 返回的是**同一个 Proxy 对象**，重新赋值相当于切断引用：

```js
let state = reactive({ count: 0 })

// ❌ 失效
state = reactive({ count: 1 })  // state 指向全新的 Proxy，原来的响应式连接丢失
// 模板仍然引用原来的 Proxy，不会更新

// ✅ 正确
state.count = 1  // 修改现有 Proxy 的属性
Object.assign(state, { count: 1 })  // 批量更新
```

**本质原因**：reactive 返回的 Proxy 是单例的，模板/计算属性/watch 都绑定到了这个具体的 Proxy 实例上。赋新值只是让变量指向了另一个对象，绑定的那些依赖仍然盯着旧的 Proxy。

这也是为什么在 options API 的 `data()` 中 return 的对象，Vue 会在初始化时递归用 reactive 包装一次，后续不允许替换整个对象——只能修改属性。

### Q: ref 和 reactive 可以混用吗？在 composable 中怎么选择？

**回答要点：**

**可以混用**，ref 在 reactive 中会自动解包：

```js
const count = ref(0)
const state = reactive({ count })

state.count // 0 —— ref 自动解包，不需要 state.count.value
state.count = 1
count.value // 1 —— 双向关联
```

但只有**在 reactive 内部时**才自动解包，在普通对象或另一个 ref 中不会：

```js
const count = ref(0)
const obj = { count }  // 普通对象
obj.count // RefImpl 对象，不会自动解包
```

**Composable 中的选择建议：**

- **返回单个值** → 用 `ref`（比如倒计时、开关状态）
- **返回一组相关状态** → 用 `reactive`（比如表单数据、筛选条件）
- **不确定怎么选** → 用 `ref`，它更灵活（解构不丢、传参方便、可重新赋值）
- **Composable 对外暴露** → 统一用 `ref`，调用方不关心内部实现

```js
// ✅ 推荐：composable 统一用 ref
function useCounter() {
  const count = ref(0)
  const double = computed(() => count.value * 2)
  const increment = () => count.value++
  return { count, double, increment }  // 解构后响应式不丢
}

// ❌ 不推荐：composable 用 reactive + toRefs
function useCounter() {
  const state = reactive({ count: 0, double: 0 })
  // 需要手动 toRefs 才能解构
  return toRefs(state)
}
```

Vue 官方（VueUse 库）也倾向于在 composable 中全部用 `ref`，保持统一的访问方式（都需要 `.value`），避免调用方困惑。

### Q: readonly(ref) 和 computed 有什么区别？

**回答要点：**

两者都返回只读值，但语义不同：

| <br /> | readonly      | computed    |
| ------ | ------------- | ----------- |
| 来源     | 基于已有响应式数据     | 自定义计算逻辑     |
| 值变化条件  | 源数据变化         | 依赖的响应式数据变化  |
| 可写     | 否（只读）         | 可自定义 setter |
| 典型场景   | 暴露状态给外部但不允许修改 | 派生状态        |

```js
const count = ref(0)

// readonly — 只读"镜像"
const readOnlyCount = readonly(count)
readOnlyCount.value++ // ❌ 报错：target is readonly

// computed — 派生计算
const double = computed(() => count.value * 2)

// computed 可自定义双向
const double = computed({
  get: () => count.value * 2,
  set: (val) => { count.value = val / 2 }
})
```

**实际用途**：在 composable 中用 `readonly` 暴露状态，防止外部直接修改内部状态，强制通过你提供的方法来变更：

```js
function useCounter() {
  const count = ref(0)
  const increment = () => count.value++
  return {
    count: readonly(count),  // 外部只能读，不能直接改
    increment
  }
}
```

### Q: Vue 2 的 data 和 Vue 3 的 ref/reactive 有什么本质区别？

**回答要点：**

| <br />   | Vue 2 `data()`          | Vue 3 `ref` / `reactive` |
| -------- | ----------------------- | ------------------------ |
| 实现机制     | `Object.defineProperty` | `Proxy`                  |
| 新增属性     | 非响应式（需 `Vue.set`）       | 自动响应式                    |
| 数组变更     | 不能直接下标赋值                | 原生支持                     |
| 响应式粒度    | 组件级                     | 任意层级                     |
| 与组合式 API | 不兼容                     | 原生支持                     |

**更深层的区别：**

1. **Vue 2 的 data 是在组件实例上挂载的**：`this.count = 1` 实际上是在组件实例上定义响应式属性，所有属性都挂在 `this` 上
2. **Vue 3 的 ref/reactive 是独立的**：不依赖组件实例，可以在任意 JS 文件中使用，这为跨组件共享状态提供了基础
3. **追踪粒度不同**：Vue 2 的 `defineProperty` 需要预先声明所有属性，Vue 3 的 Proxy 可以拦截任意属性的增删

### Q: Proxy 相比 Object.defineProperty 有哪些优势和劣势？

**回答要点：**

**优势：**

| 能力 | Object.defineProperty | Proxy |
|------|----------------------|-------|
| 拦截新增属性 | ❌ 需要 Vue.set | ✅ 自动拦截 |
| 数组下标操作 | ❌ 无法检测 arr[i] = x | ✅ 原生拦截 |
| 数组 length 变更 | ❌ 无法检测 | ✅ 拦截 length 变化 |
| 删除属性 | ❌ 无法拦截 delete | ✅ 拦截 deleteProperty |
| 拦截更多操作 | ❌ 仅 get/set | ✅ in、delete、ownKeys、has 等 13 种 |
| 一次性初始化开销 | 小（仅遍历已有属性） | 大（创建 Proxy 实例） |

**Proxy 最大的优势——能拦截的操作种类远多于 defineProperty：**

```js
const handler = {
  get(target, key) {},           // 读取属性
  set(target, key, value) {},    // 设置属性（含新增）
  deleteProperty(target, key) {}, // delete obj.key
  has(target, key) {},            // 'key' in obj
  ownKeys(target) {},            // Object.keys / for...in
  apply(target, thisArg, args) {}, // 函数调用（可用于函数劫持）
  construct(target, args) {},      // new 操作
}
```

**Vue 2 用的 defineProperty 只有 get/set，所以大量操作无法拦截：**

```js
// Vue 2 无法拦截的典型场景
const vm = new Vue({ data: { items: ['a'] } })
vm.items[0] = 'b'    // ❌ 不会触发更新
vm.items.length = 0  // ❌ 不会触发更新
vm.newKey = 1        // ❌ 不会触发更新（需要 Vue.set）

// Vue 3 Proxy 全部可以拦截
const state = reactive({ items: ['a'] })
state.items[0] = 'b' // ✅ 触发更新
state.items.length = 0 // ✅ 触发更新
state.newKey = 1     // ✅ 触发更新
```

**劣势：**

1. **兼容性** — Proxy 无法 polyfill，不支持 IE11。这是 Vue 3 放弃 IE11 的关键原因。如果你的目标用户还在用 IE，Vue 2 是唯一选择。

2. **Proxy 对象不等于原对象** — 每次 `reactive(obj)` 返回的都是一个新的 Proxy 对象，和原对象 `===` 比较为 false：
   ```js
   const raw = { count: 0 }
   const proxy = reactive(raw)
   console.log(proxy === raw) // false
   ```

3. **Proxy 的 this 指向问题** — 当对象上的方法通过 Proxy 调用时，this 指向 Proxy 本身而不是原始对象。在极少数场景下会出问题：
   ```js
   const obj = {
     count: 0,
     getCount() {
       return this.count  // this 指向 Proxy，不是 raw obj
     }
   }
   const proxy = reactive(obj)
   proxy.getCount() // ✅ 正常工作（this 是 Proxy，能触发追踪）
   ```

4. **性能开销** — Proxy 拦截操作比 defineProperty 更重（需要经过 handler）。但 Vue 3 做了大量优化来抵消这个开销：比如懒代理（访问到才代理）和 ReactiveFlags 缓存。

**面试回答策略：**
- 先说 Proxy 的**核心优势**——数组操作、属性增删这些 Vue 2 没法做的场景
- 再提 **IE11 兼容性**——这是 Vue 3 放弃 IE 的根源
- 最后说 **Proxy 不等于原对象**——点出这个容易被忽略的点，体现深度

### Q: ref(() => 1) 和 reactive(() => ({})) 会怎样？

**回答要点：**

取决于 Vue 3 内部的 `isObject` 判断：

```js
// packages/shared/src/index.ts
export const isObject = (val) => val !== null && typeof val === 'object'
```

关键点：`typeof function === 'function'`，不是 `'object'`。

**`ref(() => 1)`：**
```js
const fn = ref(() => 1)
fn.value // () => 1（函数本身，没有被 reactive 包裹）
fn.value() // 1
```

`ref` 内部判断 `isObject(() => 1)` 为 `false`，函数被当作**普通值**直接存储，不会走 `reactive()`。`.value` 拿到的就是函数本身，等价于：
```js
const fn = ref(null)
fn.value = () => 1
```

**`reactive(() => ({a:1}))`：**

首先有语法问题——箭头函数的 `{a:1}` 的花括号会被识别为函数体而不是对象字面量（`a:1` 会被当成 label 语句）。正确写法是 `reactive(() => ({a:1}))`。

修正后，`typeof (() => ({}))` 仍然是 `'function'`，`isObject` 返回 `false`。Vue 3 在开发环境会 warn：

```
@vue/reactivity: value cannot be made reactive: () => ({a:1})
```

然后直接**原样返回函数**，不做任何响应式代理。

**总结：**

| 表达式 | 结果 | 说明 |
|--------|------|------|
| `ref(() => 1)` | ref，`.value` 是函数 | 函数被视作普通值，不 reactive |
| `reactive(() => ({}))` | ❌ warn，返回原函数 | reactive 只处理对象 |
| `reactive({ fn: () => 1 })` | ✅ Proxy，fn 是对象上的属性 | 对象内部的函数是正常属性，整个对象被代理 |
| `ref({ fn: () => 1 })` | ref，内部调用 reactive | 对象走 reactive，fn 在 Proxy 中 |

**面试要点**：Vue 3 的 `isObject` 严格区分 `object` 和 `function`。这也是为什么需要 `ref`——基本类型和函数都不能直接 `reactive`，必须包一层 `{ value: ... }`。
