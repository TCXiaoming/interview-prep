# 微前端

## 核心概念

微前端是将前端应用拆分成多个可以独立开发、独立部署、独立运行的子应用的架构模式。本质是"前端领域的微服务"，解决的是**大型团队协作下的工程效率问题**，不是技术炫技。

### 主流方案对比

| 方案                | 隔离方式                    | 通信机制                | 性能             | 适用场景                   |
| ----------------- | ----------------------- | ------------------- | -------------- | ---------------------- |
| iframe            | 天然隔离                    | postMessage         | 差（独立文档、资源重复加载） | 遗留系统集成、安全要求高           |
| single-spa        | 无隔离                     | 自定义事件/全局变量          | 好              | 轻量方案、自己控制隔离            |
| qiankun           | Proxy 沙箱 + Shadow DOM   | props + GlobalState | 较好             | 企业级、需要开箱即用             |
| Module Federation | 无隔离（共享运行时）              | 直接调用                | 最好             | 同团队、技术栈统一              |
| wujie             | iframe + Web Components | props + EventBus    | 较好             | 需要严格隔离但不想 iframe 的性能损耗 |

### JS 隔离（沙箱）

**Proxy 沙箱（qiankun 的做法）**：

```js
// 假沙箱：用 Proxy 代理 window，每个子应用操作的是自己的 fakeWindow
const fakeWindow = Object.create(null);
const proxy = new Proxy(fakeWindow, {
  get(target, key) {
    return target[key] || window[key]; // fallback 到真实 window
  },
  set(target, key, value) {
    target[key] = value; // 写入假 window，不影响真实 window
    return true;
  }
});
// 子应用在 proxy 上执行，不会污染全局
```

关键点：

- 不是真正的隔离，是"代理 + fallback"，读的时候兜底真实 window，写的时候写到 fakeWindow
- 有多例模式（每个子应用一个 fakeWindow）和单例模式（共用一个 fakeWindow，切换时 diff 还原）
- 无法拦截所有 API，比如 `document.getElementById` 还是操作真实 DOM

**Snapshot 沙箱（快照沙箱）**：

```js
// 激活前：把 window 当前状态拍个快照
const snapshot = { ...window };
// 子应用运行，修改 window
// 失活时：遍历 window，把多出来的属性删掉，少的补回来
// 恢复到快照状态
```

缺点：只能支持单实例，无法同时运行两个子应用。

### CSS 隔离

**方案对比**：

1. **CSS Modules / BEM 命名约定**：最简单但不彻底，依赖开发者自觉，容易冲突
2. **Shadow DOM**：浏览器原生隔离，但全局样式（如 body 字体）无法穿透，子应用 UI 框架可能出问题
3. **CSS-in-JS**：天然隔离，但运行时开销大
4. **Dynamic Stylesheet（qiankun 做法）**：
   - 子应用激活时，将 `<style>` 插入 document
   - 子应用失活时，将对应的 `<style>` 移除
   - 同时给子应用容器加 `div` 前缀选择器做作用域限定
   - 本质是运行时切换样式表，不是真正的隔离
5. **Shadow DOM（wujie 做法）**：把子应用渲染在 Web Components 的 ShadowRoot 里，CSS 天然隔离

### 子应用通信

**常见方式**：

```js
// 1. props 传参（父子之间，最直接）
registerMicroApp({
  name: 'app1',
  props: {
    token: 'xxx',
    user: { name: '张三' }
  }
});

// 2. 全局状态（跨子应用，qiankun 的 GlobalState）
const actions = initGlobalState({ user: null });
actions.onGlobalStateChange((state) => {
  console.log('用户变了:', state.user);
});
actions.setGlobalState({ user: { name: '李四' } });

// 3. 自定义事件（解耦）
window.dispatchEvent(new CustomEvent('user-change', { detail: { name: '李四' } }));
window.addEventListener('user-change', (e) => { /* ... */ });

// 4. URL 参数 / 路由（天然的跨应用通信）
// 通过路由跳转传递参数，子应用监听路由变化
```

**子应用间直接交互的场景：**

```js
// 场景：子应用 A 触发"订单已创建"，子应用 B 更新订单列表

// 方案一：通过主应用 GlobalState 桥接（推荐）
// 子应用 A
props.onGlobalStateChange((state) => { /* ... */ }, true);
props.setGlobalState({ newOrder: { id: 123 } });

// 方案二：自定义事件（适合松耦合）
// 子应用 A（触发方）
window.dispatchEvent(new CustomEvent('order-created', {
  detail: { orderId: 123 }
}));

// 子应用 B（监听方）— 注意 unmount 时要 removeEventListener
window.addEventListener('order-created', (e) => {
  refreshOrderList(e.detail.orderId);
});

// 方案三：共享路由状态（适合导航类交互）
// 子应用 A 跳转到子应用 B 的某个页面
// 通过主应用路由跳转：history.push('/appB/orders/123')
```

**跨应用状态共享的最佳实践：**

```
子应用 A ──setState──→ GlobalState ──onChange──→ 子应用 B
                      （主应用托管）
                          ↑
                      localStorage（持久化兜底）
```

- **简单状态**（token、用户信息）→ GlobalState 或 localStorage
- **实时状态**（通知、消息）→ WebSocket / EventSource，主应用统一管理，分发给子应用
- **复杂状态**（表单数据、草稿）→ 子应用自己管理，只在需要时通过 GlobalState 通知其他子应用

不管哪个方案，子应用都需要暴露标准生命周期：

```js
// 子应用导出
export async function bootstrap() {
  console.log('首次加载');
}

export async function mount(props) {
  // 挂载，render 到指定容器
  ReactDOM.render(<App />, props.container);
}

export async function unmount() {
  // 卸载，清理副作用
  ReactDOM.unmountComponentAtNode(container);
}

export async function update(props) {
  // 可选，主应用手动触发更新
}
```

### shared（共享依赖）

Module Federation 和 qiankun 都需要处理依赖共享：

```
主应用 React 18.2 + 子应用 React 18.2 → 共享同一份，不重复加载
主应用 React 18.2 + 子应用 React 17.x → 不能共享，各自加载
```

实现思路：

- 构建时：Module Federation 的 `shared` 配置，版本兼容时共享
- 运行时：qiankun 通过 import-html-entry 解析子应用 HTML，把公共依赖替换成主应用已加载的版本

**qiankun 共享依赖的具体做法：**

qiankun 通过 `expose-loader` 或 webpack 的 `externals` 将公共库（React、Vue）挂在 window 上，子应用构建时将这些库标记为 externals，运行时直接从主应用环境获取：

```js
// 主应用 webpack 配置
module.exports = {
  externals: {
    react: 'React',
    'react-dom': 'ReactDOM',
    vue: 'Vue',
  }
};

// 子应用 webpack 配置 — 不要重复打包公共库
module.exports = {
  externals: {
    react: 'React',
    'react-dom': 'ReactDOM',
  }
};
```

**版本冲突的坑**：主应用 React 16 + 子应用 React 18，如果强行共享会导致子应用运行时崩溃（hooks 机制变化）。qiankun 不会自动拦截版本不兼容的共享，需要人工确保版本一致或在子应用中独立打包。

**推荐做法：**

- 同版本库 → externals 共享，不重复加载
- 不同版本库 → 子应用独立打包，各自加载
- 小工具库（lodash、dayjs）→ 主应用统一提供，子应用 externals
- UI 组件库（antd、element）→ 子应用独立打包（版本易冲突，且样式隔离难处理）

### 预加载

qiankun 支持预加载：在浏览器空闲时提前加载子应用的静态资源（JS/CSS），等用户真正点击导航时资源已经缓存好了，体验接近单体应用。

```js
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([...]);
start({ prefetch: 'all' }); // 预加载所有子应用资源
```

## qiankun 隔离方案深度分析

### JS 隔离方案对比

| 方案               | 版本               | 原理                                                   | 优点         | 缺点                     |
| ---------------- | ---------------- | ---------------------------------------------------- | ---------- | ---------------------- |
| Snapshot 沙箱      | 单例模式（qiankun v1） | 激活时快照 window，失活时 diff 还原                             | 实现简单，兼容性好  | 只能支持一个子应用实例；遍历所有属性的开销大 |
| Proxy 沙箱（Legacy） | 单例模式             | Proxy 代理 window，写入 fakeWindow，读取 fallback 到真实 window | 比快照轻量，不用遍历 | 单实例，两个同种子应用不能共存        |
| Proxy 沙箱         | **多例模式（v2 默认）**  | 每个子应用独立的 fakeWindow，用 Proxy 隔离                       | 支持多实例共存    | 内存占用随子应用数量增加           |

**演进逻辑：** v1 用快照 → 发现慢 → v2 引入无实例 Proxy → 然后发现多个子应用需要同时显示 → 多例 Proxy。每一步都是踩坑后的升级。

### Proxy 沙箱的局限与优化

**五个漏网之鱼（面试高频）：**

```js
// 1. document 操作 — 沙箱拦截不了
document.title = '子应用标题';           // 会改主应用的 title
document.querySelector('body').style.background = 'red'; // 全局污染

// 2. DOM 事件监听 — 沙箱拦截不了 
document.addEventListener('click', handler);  // unmount 后不清理就泄漏

// 3. 定时器 — 沙箱拦截不了
setInterval(cb, 1000);  // unmount 后继续执行

// 4. history / location — 沙箱虽然能代理，但不会自动还原
history.pushState(null, '', '/app1/page'); // 路由状态需要手动管理

// 5. window 上已存在的属性 — 沙箱的 get fallback 读的是原始属性
// 子应用写了 window.JSON = 'hacked' → 写入 fakeWindow
// 但其他子应用读 window.JSON → 读的是真实 window.JSON（未被篡改，隔离生效）
// 但子应用自己读 window.JSON → 读的是 fakeWindow 里的 'hacked'（自洽）
// 这里最容易被绕晕：每个子应用看到的是自己的 fakeWindow，不要跨子应用假设
```

**工程优化方案：**

```
1. 运行时补丁：在子应用 mount 时，劫持 document.createElement 等 API
   → 把子应用的 DOM 操作限制在自己的容器内
   → 但 patch 多了影响性能，且可能和子应用的 UI 框架冲突

2. 静态检查：CI 阶段用 ESLint 检查子应用代码
   → 禁止直接操作 document.body、window.addEventListener 等
   → 从源头避免问题，比运行时兜底更可靠

3. unmount 强制清理：在子应用 unmount 时
   → 遍历并清除子应用注册的所有事件监听（qiankun 内部不会做）
   → 清除所有定时器
   → 需要子应用配合暴露 cleanup 方法
```

**推荐的工程级方案**是"**约束 + 兜底**"：

```js
// 约束层（CI/CD 阶段）
// .eslintrc.js — 禁止危险操作
module.exports = {
  rules: {
    'no-restricted-globals': [
      'error',
      { name: 'document', message: '子应用中不要直接操作 document' },
      { name: 'window', message: '子应用中不要直接操作 window' },
    ],
    'no-restricted-properties': [
      'error',
      { property: 'addEventListener', object: 'document' },
    ],
  },
};

// 兜底层（运行时）
export async function mount(props) {
  // 记录 mount 时注册的全局事件
  const originalAddListener = window.addEventListener.bind(window);
  const listeners = [];
  window.addEventListener = (type, handler) => {
    listeners.push({ type, handler });
    originalAddListener(type, handler);
  };

  render(<App />, props.container);
}

export async function unmount() {
  // 清理所有注册的全局事件
  listeners.forEach(({ type, handler }) => {
    window.removeEventListener(type, handler);
  });
  ReactDOM.unmountComponentAtNode(container);
}
```

### CSS 隔离方案深度对比

| 方案                       | 实现方式              | 隔离效果      | 性能影响             | 工程复杂度        |
| ------------------------ | ----------------- | --------- | ---------------- | ------------ |
| 动态样式表（qiankun ScopedCSS） | 激活插入/失活移除 + 选择器前缀 | ⚠️ 有漏洞    | 几乎无              | 低，qiankun 内置 |
| Shadow DOM               | 挂载到 ShadowRoot    | ✅ 彻底      | 中，样式无法复用的场景会重复   | 中，需修改子应用挂载方式 |
| CSS-in-JS                | 样式和组件绑定           | ✅ 彻底      | 高，运行时注入 style 标签 | 依赖 UI 框架     |
| 命名约定（BEM/CSS Modules）    | 构建时加唯一前缀          | ✅ 彻底（约束力） | 几乎无              | 低，但依赖开发者自觉   |

**ScopedCSS 的工作原理（qiankun 默认方案）：**

qiankun 的 `experimentalStyleIsolation: true` 会在子应用容器上设置一个 `data-xxx` 属性，然后通过 postcss 给子应用所有 CSS 选择器加上这个属性前缀：

```css
/* 原始的 */
.header .title { color: red; }

/* ScopedCSS 处理后 */
div[data-qiankun-app1] .header .title { color: red; }
```

**ScopedCSS 的三大漏洞：**

```
漏洞1: body/html 选择器
  body { background: #fff } → 不会被加前缀
  → 子应用的 body 样式会"泄漏"到主应用

漏洞2: @keyframes / @font-face
  @keyframes slide { ... } → 不会被加 scope
  → 子应用和主应用如果有同名 keyframes 名，会冲突

漏洞3: 动态注入的 style
  const style = document.createElement('style');
  style.textContent = '.dynamic { color: red }';
  document.head.appendChild(style);
  → 运行时动态创建的 style 标签不会被 ScopedCSS 处理
```

**工程优化方案：**

**方案一：ScopedCSS + 手动补救（推荐）**

```css
/* 子应用样式 — 避免写全局选择器 */
❌ body { background: #fff; }
❌ .el-dialog__wrapper { z-index: 2000; }

✅ #app1-container { background: #fff; }  /* 带容器选择器 */

/* 使用 CSS 自定义属性穿透（如果需要继承主应用主题） */
:root {
  --theme-primary: #1890ff; /* 主应用定义，子应用用 var() 引用 */
}
```

**方案二：Shadow DOM（严格隔离）**

```js
// 子应用挂载到 ShadowRoot 下
import { createApp } from 'vue';

export async function mount(props) {
  const container = props.container.querySelector('#app');
  // 创建 ShadowRoot
  const shadowRoot = container.attachShadow({ mode: 'open' });
  // 在 ShadowRoot 内挂载
  const app = createApp(App);
  app.mount(shadowRoot.querySelector('#shadow-app'));
}
```

缺点：

- antd/element-plus 的弹窗组件（Dialog/Drawer）会 append 到 body，逃出 Shadow DOM
- 全局样式（字体、iconfont）在 Shadow DOM 内不生效，需要手动注入
- 子应用内的 `document.getElementById` 可能找不到元素（因为挂在 ShadowRoot 下）

**方案三：CSS 变量 + BEM 命名（最轻量）**

```scss
// 子应用所有选择器带唯一前缀
.app1-header { ... }
.app1-header__title { ... }

// 全局样式只通过 CSS 自定义属性穿透
.app1-container {
  color: var(--app1-text-color, #333);
}
```

**三种方案的选择策略：**

```
项目类型                    → 推荐方案
同一公司不同部门的子应用      → ScopedCSS + BEM（够用，简单）
接入第三方/外部系统           → Shadow DOM（需要严格隔离）
子应用和主应用共用主题/组件库   → CSS 变量 + 命名约定（共享最方便）
```

### 隔离方案的综合评估

**qiankun 的隔离不是 100% 的，面试中不要夸大。** 说出来"我们做了什么隔离、有哪些漏网之鱼、怎么兜底"才是好的回答。

一个真实项目的隔离清单示例：

```
✓  JS 隔离：Proxy 沙箱（多例模式），隔离 window 读写
✗  未隔离：document 操作、事件监听、定时器
  → 兜底：CI 阶段 ESLint 禁止直接操作 document
  → 兜底：子应用 unmount 时清理所有全局事件和定时器
✓  CSS 隔离：experimentalStyleIsolation 开启（ScopedCSS）
✗  未隔离：body 选择器、@keyframes、动态 style
  → 兜底：CSS 规范约定，Code Review 时检查
  → 兜底：避免子应用写全局样式
```

## 常见追问

- qiankun 的 Proxy 沙箱能隔离所有全局变量吗？有什么漏网之鱼？
- 微前端子应用之间如何共享用户登录态？
- 为什么 iframe 性能差？差在哪？
- Module Federation 和微前端有什么关系？算是微前端吗？
- 子应用静态资源路径怎么处理？CSS 里的图片路径怎么修正？
- 如何实现子应用的按需加载和懒加载？

## 回答要点

**Proxy 沙箱的局限**：能隔离 window 上的属性读写，但无法隔离 `document`、`addEventListener`、`MutationObserver` 等。比如子应用操作 `document.body.style.background` 会直接影响主应用。qiankun 通过 `ScopedCSS` 和动态样式表来做 CSS 隔离，但不是 100% 完美。

**共享登录态**：通常用主应用 props 传递 token，或通过 GlobalState 管理。也可以用 cookie（同域情况下子应用直接读 cookie），但跨域时得走 postMessage 或统一网关。

**iframe 性能差的原因**：每个 iframe 是独立的浏览器上下文（browsing context），有自己的 window、document、渲染进程。意味着：重复加载公共库（React 加载 N 次）、无法共享内存状态、路由同步要手动实现（iframe 内路由变化主应用感知不到）、通信只能走 postMessage（异步、有序列化开销）。

**Module Federation 算不算微前端**：从广义上算，但它更侧重于"模块级别的代码共享"，不解决 JS/CSS 隔离问题。适合同团队内的代码复用，不适合需要严格隔离的场景（比如接入第三方应用）。

**静态资源路径**：子应用部署在独立域名下，CSS 里的 `url(./img/bg.png)` 需要修正为绝对路径。qiankun 在加载子应用 HTML 时会自动处理 `<link>`、`<script>`、`<img>` 的路径，加上子应用的 base URL。但 CSS 里内联的 `url()` 需要子应用构建时配置 `publicPath`，或者运行时用 `__webpack_public_path__` 动态设置。

## 常见坑点（踩坑经验）

### 1. 子应用切换导致全局事件和定时器泄漏

子应用 unmount 时，**不会自动清理**全局事件监听和定时器。这是最常见的泄漏根源：

```js
// ❌ 子应用 unmount 后，监听器还留在主应用里
useEffect(() => {
  window.addEventListener('resize', handleResize);
  const timer = setInterval(polling, 3000);
  return () => {
    // ✅ 必须在 unmount 时手动清理
    window.removeEventListener('resize', handleResize);
    clearInterval(timer);
  };
}, []);
```

坑点：React 的 `useEffect` 清理函数在 unmount 阶段会执行，但第三方库（如 echarts、D3）的全局监听可能绑定在 window/document 上，容易遗漏。**建议在子应用入口统一做清理检查。**

### 2. 子应用切换导致 React 17/18 的 `createRoot` 重复调用

```js
// ❌ 子应用 mount 时每次都 createRoot，第二次会报错
let root;
export async function mount(props) {
  root = createRoot(props.container);
  root.render(<App />);
}
export async function unmount() {
  root.unmount(); // 必须调用 unmount 而不是 unmountComponentAtNode
  root = null;
}
```

qiankun 的子应用可能会多次 mount/unmount（切换页面再切回来），如果不在 unmount 时销毁 root，第二次 mount 时 `createRoot` 会打印 warning 且行为不可预期。

### 3. 路由冲突：子应用路由和主应用路由互相干扰

```js
// ❌ 主应用和子应用都在监听 hashchange/popstate
// 子应用内部的路由变化可能会触发主应用路由重新匹配

// ✅ 子应用路由加前缀隔离
const router = createRouter({
  history: createWebHistory('/app1'), // 子应用所有路由都在 /app1 下
});
```

qiankun 要求子应用匹配 activeRule 时才激活，但如果子应用内部用了 `createWebHistory()` 不带 base，当路由切换时可能触发主应用的路由守卫，导致循环激活。

**解决：** 子应用路由 base 必须和 qiankun 的 activeRule 一致；主应用和子应用不要同时监听 popstate。

### 4. CSS 隔离不彻底

qiankun 的 ScopedCSS 是通过**给子应用容器加 data 属性 + 选择器前缀**来实现的：

```css
/* 子应用原本的样式 */
.title { color: red; }

/* qiankun 处理后 */
div[data-qiankun-app1] .title { color: red; }
```

**三个漏洞：**

- **body/html 选择器** — `body { background: #fff }` 不会被加前缀，会穿透影响主应用
- **@media 中的选择器** — 部分版本不支持
- **动态插入的 style** — 子应用运行时通过 JS 插入的 `<style>` 标签，ScopedCSS 不会处理

**解决：** 子应用不要写全局样式和 body 样式；动态插入的样式手动加 scope；或在子应用根节点设 `contain: strict`。

### 5. 子应用 resource 路径错误（CSS 图片、字体）

子应用部署在独立域名/CDN 后，CSS 中的相对路径会错乱：

```css
/* 子应用 CSS */
background: url(./images/bg.png); /* 主应用加载时，这个路径相对于主应用域名，找不到 */

/* 解决：子应用构建时设置 publicPath */
// vue.config.js
module.exports = {
  publicPath: '//cdn.example.com/sub-app1/',
};

// webpack
output: {
  publicPath: '//cdn.example.com/sub-app1/',
}
```

如果忘了配 publicPath，图片和字体全部 404。**这是 qiankun 最常见的踩坑点**。

### 6. 子应用间的数据同步延迟

GlobalState 是**同步更新**的，但子应用的 setState 和另一个子应用的 onStateChange 回调之间可能有微任务延迟：

```js
// 子应用 A
props.setGlobalState({ token: 'new-token' });

// 子应用 B — 不能假设此时 props 已经更新了
// 需要用 onGlobalStateChange 监听变化，而不是直接读 props
```

### 7. qiankun + Vite 的兼容性问题

qiankun 基于 `import-html-entry`，需要通过 HTML 入口文件解析子应用的 JS/CSS。但 Vite 开发模式基于 ESM，返回的是 JS 模块而不是传统 script 标签，qiankun 无法直接解析。需要额外插件（如 `vite-plugin-qiankun`）来适配。

**结论**：qiankun 和 Vite 配合不如 webpack 顺畅。如果主应用是 Vite + 子应用是 webpack，或者反过来，通常会遇到问题。新项目建议先统一技术栈。

## 面试中的陷阱

- 问"你们为什么选 qiankun"不要说"因为社区用的多"，要说具体的隔离需求和团队技术栈匹配度
- 问"微前端解决了什么问题"不要泛泛说"解耦"，要说具体：比如"A 团队用 Vue、B 团队用 React，想独立发版不互相阻塞"
- 问"和 Monorepo 的区别"：Monorepo 是代码管理方式（多个包在一个仓库），微前端是运行时架构（多个应用在一个页面）。可以组合使用
