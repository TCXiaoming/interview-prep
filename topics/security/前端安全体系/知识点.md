# 前端安全体系

## 核心概念

### XSS（Cross-Site Scripting，跨站脚本攻击）

**类型：**

| 类型 | 方式 | 危害程度 |
|---|---|---|
| 存储型 | 恶意脚本存入数据库，用户访问时执行 | 最高 |
| 反射型 | 恶意脚本通过 URL 参数传入，服务端反射到页面 | 中 |
| DOM 型 | 恶意脚本通过前端 JS 操作 DOM 执行 | 中 |

**防御手段：**

1. **输入过滤/转义**
   ```js
   // 对输出到 HTML 的内容进行转义
   function escapeHtml(str) {
     return str
       .replace(/&/g, '&amp;')
       .replace(/</g, '&lt;')
       .replace(/>/g, '&gt;')
       .replace(/"/g, '&quot;')
       .replace(/'/g, '&#39;');
   }
   ```

2. **CSP（Content Security Policy）**
   ```http
   Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'; style-src 'self' 'unsafe-inline'
   ```
   - 限制脚本来源 — 只允许加载指定域名的脚本
   - 禁止内联脚本 — 消除最大的 XSS 攻击面
   - 用 nonce/hash — 允许特定的内联脚本

3. **Cookie 安全**
   ```
   Set-Cookie: sessionId=xxx; HttpOnly; Secure; SameSite=Strict
   ```
   - `HttpOnly` — JS 无法读取，防止 XSS 窃取 Cookie
   - `Secure` — 只在 HTTPS 下发送
   - `SameSite` — 防止 CSRF（见下方）

4. **框架默认防护** — React 默认转义 JSX 表达式，Vue 的 `{{ }}` 默认转义。`dangerouslySetInnerHTML` / `v-html` 要慎用。

### CSRF（Cross-Site Request Forgery，跨站请求伪造）

**攻击原理：**
用户已登录 A 站，访问恶意 B 站时，B 站向 A 站发起请求，浏览器自动带上 A 站的 Cookie。

**防御手段：**

1. **SameSite Cookie** — `SameSite=Strict` 或 `SameSite=Lax`，跨站请求不带 Cookie
2. **CSRF Token** — 服务端生成随机 Token，每次请求携带，服务端验证
3. **验证 Referer/Origin** — 检查请求来源是否合法（但 Referer 可能被篡改或不发送）
4. **自定义请求头** — AJAX 请求加自定义头（如 `X-Requested-With`），简单请求不会带自定义头

### 点击劫持（Clickjacking）

**攻击方式：** 用透明 iframe 嵌入目标网站，覆盖在一个诱导按钮上，用户点击的其实是目标网站上的操作。

**防御：**
```http
X-Frame-Options: DENY                          # 禁止任何网站嵌入
X-Frame-Options: SAMEORIGIN                    # 只允许同源嵌入
Content-Security-Policy: frame-ancestors 'none'  # CSP 版本（推荐）
```

### 其他安全威胁

| 威胁 | 说明 | 防御 |
|---|---|---|
| SQL 注入 | 通过输入恶意 SQL 语句 | 参数化查询、ORM（前端间接相关） |
| HTTPS 中间人攻击 | 窃听/篡改 HTTP 通信 | 全站 HTTPS、HSTS |
| 依赖漏洞 | 第三方库有安全漏洞 | `npm audit`、Snyk、定期更新 |
| 敏感信息泄露 | 前端代码暴露 API Key、密钥 | 环境变量、不在前端存密钥 |
| 开放重定向 | 利用重定向跳转到恶意网站 | 校验重定向目标白名单 |

### 前端 Token 认证安全

```js
// JWT 存储方案对比
// 1. localStorage — 容易被 XSS 窃取
localStorage.setItem('token', jwt);

// 2. HttpOnly Cookie — 防 XSS，但需防 CSRF
// 服务端设置 Set-Cookie: token=xxx; HttpOnly; SameSite=Strict

// 3. 双 Token 方案（推荐）
// Access Token：短期（15min），存内存
// Refresh Token：长期（7d），存 HttpOnly Cookie
// Access Token 过期后用 Refresh Token 静默刷新
```

## 常见追问

### Q: CSP 会不会影响正常业务？

**回答要点：**
会。CSP 太严格可能导致：
- 内联脚本/样式不执行（解决方案：用 nonce 或 hash）
- 第三方 SDK 加载失败（解决方案：白名单放行可信域名）
- Google Analytics、广告等第三方脚本需要单独配置

建议渐进式开启：先用 `Content-Security-Policy-Report-Only` 只报告不阻塞，收集够数据后再正式启用。

### Q: React/Vue 默认防 XSS，还需要额外措施吗？

**回答要点：**
需要。框架只防了输出转义这一层，但以下场景仍然危险：
1. `dangerouslySetInnerHTML` / `v-html` — 直接插入 HTML，框架不保护
2. `href` / `src` 中的用户输入 — `javascript:xxx` 协议
3. DOM 型 XSS — 通过 DOM API 操作导致的（框架不控制）
4. 服务端存储型 — 框架只保护渲染层，不保护数据库

框架的防护是必要的但不充分，还需要 CSP、输入校验、Cookie 安全等多层防护。

### Q: DOM 型 XSS 和其他两种有什么本质区别？

**回答要点：**
核心区别：**DOM 型 XSS 不经过服务器**，恶意代码完全在客户端通过 JS 操作 DOM 注入。

```js
// 典型场景：URL hash 被 innerHTML
// URL: https://example.com/#<img src=x onerror=alert(1)>
const hash = location.hash.slice(1);
document.getElementById('output').innerHTML = hash; // 触发 XSS
```

对比三种类型：

| 类型 | 恶意代码位置 | 经过服务器 | CSP 能否防御 |
|---|---|---|---|
| 存储型 | 数据库 | 是 | 能（限制脚本来源） |
| 反射型 | URL 参数 | 是（服务器原样返回） | 能 |
| DOM 型 | URL hash / 用户输入 | 否（纯客户端） | 不能（没有内联 script 标签） |

DOM 型 XSS 的防御靠代码层面：避免 `innerHTML`、`document.write` 等危险 API，用 `textContent` 替代，对用户输入做转义。

### Q: 前端怎么处理敏感数据？

**回答要点：**
1. **不在前端存储敏感数据** — API Key、密钥、密码绝不放在前端代码里
2. **环境变量** — 敏感配置用 `.env` 文件，通过构建工具注入，不提交到 Git
3. **传输加密** — 全站 HTTPS，敏感接口额外加密
4. **最小权限** — 前端只获取需要的数据，后端做数据脱敏
5. **日志脱敏** — 前端错误日志中不能包含用户隐私信息（手机号、身份证等）

## 回答要点总结

1. XSS 和 CSRF 是必问题，要能说清攻击原理和防御手段
2. CSP 是现代 Web 安全的核心，了解其配置方式
3. Token 认证方案（特别是双 Token）要能说清楚
4. 金融行业（大疆如果有支付相关业务）对安全要求更高，可以延伸讨论
