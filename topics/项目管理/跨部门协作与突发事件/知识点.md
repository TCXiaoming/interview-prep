# 跨部门协作与突发事件处理

## 核心概念

### 跨部门协作的常见场景

1. **产品需求对接** — 前端与产品、设计、后端的协作
2. **技术方案评审** — 与架构组、安全组、运维组的协调
3. **紧急需求插入** — 业务方突然加塞需求
4. **依赖方阻塞** — 后端接口没 ready、设计稿没出、第三方服务不稳定
5. **资源争夺** — 多个业务线抢同一个开发资源

### 协作中的关键原则

1. **信息对齐** — 确保各方对需求理解一致，避免"我以为你知道"
2. **风险前置** — 提前暴露技术风险和时间风险，不要等到 deadline 才说做不完
3. **接口契约先行** — 前后端协作中，先对齐接口文档（OpenAPI/Swagger），再各自开发
4. **定期同步** — 周会/站会不是形式，是确保信息流通的机制

### 突发事件分类与处理

| 类型 | 示例 | 处理思路 |
|---|---|---|
| 生产事故 | 线上白屏、接口挂了 | 定位 → 止血 → 修复 → 复盘 |
| 需求变更 | 上线前一天改交互 | 评估影响 → 沟通成本 → 协商排期 |
| 人员变动 | 核心开发离职/请假 | 知识文档化 → 交接 → 调整排期 |
| 依赖方延误 | 后端接口延期交付 | 评估影响 → mock 先行 → 追踪进度 |

## 常见追问

### Q: 你遇到过跨部门协作的困难吗？怎么解决的？

**回答框架（STAR）：**
- **Situation**：什么项目、和哪些部门协作、遇到什么问题
- **Task**：你的角色是什么、需要达成什么目标
- **Action**：你具体做了什么（沟通方式、推动机制、工具手段）
- **Result**：最终结果、量化数据、经验沉淀

**关键点：**
- 不要说"我沟通能力强"，要举具体例子
- 强调你主动推动的行动，不是被动等待
- 如果有失败的案例也可以说，重点是学到了什么

### Q: 后端接口没 ready，前端怎么推进？

**回答要点：**
1. **接口契约先行** — 前后端先对齐接口文档（字段、类型、格式），用 OpenAPI 规范
2. **Mock 数据先行** — 用 Mock.js / MSW / 自建 Mock Server，前端不阻塞
3. **联调窗口约定** — 约定一个时间节点集中联调，而不是边做边调
4. **接口自动化测试** — 写接口级别的测试，联调时能快速发现不一致

### Q: 线上出了严重事故，你怎么处理？

**回答框架：**
1. **止血优先** — 先回滚/降级，恢复服务，不要在现场修 bug
2. **定位问题** — 看日志、监控、链路追踪，快速定位根因
3. **通知相关方** — 同步产品、运营、客服，让他们知道影响范围和预计恢复时间
4. **修复上线** — 修完后走正常流程上线，不能因为急就跳过测试
5. **复盘** — 写故障报告，分析根因、改进措施、责任人，形成闭环

### Q: 你是怎么管理前端团队的？

**回答要点：**
- **任务拆解** — 大需求拆成小任务，每个任务有明确的负责人和 deadline
- **Code Review** — 建立 Review 机制，不只是检查代码质量，也是知识传递
- **技术分享** — 定期组织分享，提升团队整体能力
- **人才培养** — 给有潜力的人更多挑战性的任务，做 mentor
- **规范落地** — 统一技术栈、代码规范、Git 规范，降低协作成本

### Q: 多个紧急需求同时来，你怎么排优先级？

**回答要点：**
1. **影响范围** — 影响用户多的优先
2. **紧急程度** — 有明确 deadline 的优先
3. **技术依赖** — 被其他模块依赖的优先
4. **投入产出比** — 开发成本低但收益大的优先
5. **向上沟通** — 如果资源确实不够，带着方案找领导决策，不是自己硬扛

## 回答要点总结

1. 用具体案例说话，STAR 结构最清晰
2. 体现主动推动能力，不是被动等别人
3. 有复盘意识 — 不仅解决问题，还沉淀方法
4. 量化结果 — 时间缩短了多少、效率提升了多少、影响范围多大
5. 大疆作为硬件+软件公司，跨部门协作场景多（硬件、固件、云端、客户端、前端），可以延伸讨论
