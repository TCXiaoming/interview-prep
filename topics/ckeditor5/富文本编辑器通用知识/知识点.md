# 富文本编辑器通用知识

## 核心概念

### 1. contentEditable

浏览器提供的原生富文本编辑能力，通过给 DOM 元素设置 `contenteditable="true"` 使其可编辑。

```html
<div contenteditable="true">
  <p>这是一个可编辑的段落</p>
</div>
```

**致命缺陷**：
- 各浏览器实现不一致，相同操作产生的 HTML 不同
- 光标行为不可控，嵌套结构下容易出现光标丢失
- 无法精细控制粘贴内容
- 撤销/重做行为不可控（`document.execCommand` 已废弃）

所以现代富文本编辑器**不直接用 contentEditable 做编辑逻辑**，而是把它当作一个"壳"，内部用自定义数据模型管理内容。

### 2. 富文本编辑器的两种架构

#### 基于 DOM 的架构（CKEditor 4、TinyMCE 早期版本）

直接操作浏览器 DOM，依赖 `contentEditable` + `document.execCommand`。

优点：实现简单，兼容性好
缺点：浏览器差异大，难以做协同编辑，难以精确控制输出

#### 基于 Model 的架构（现代主流）

维护独立的数据模型，DOM 只是 View 层的渲染结果。

```
用户输入 → 拦截 → 修改 Model → Model 变更通知 → 重新渲染 View(DOM)
```

代表：CKEditor 5、ProseMirror、Slate、Quill、TipTap

优点：
- 输出格式可控（不依赖浏览器行为）
- 可以做协同编辑（OT/CRDT）
- 浏览器差异小（DOM 只是渲染目标）
- 撤销/重做由自己控制

---

### 3. 常见编辑器对比

| 编辑器 | 架构 | 数据模型 | 协同支持 | 框架集成 |
|--------|------|---------|---------|---------|
| **CKEditor 5** | Model-View-Conversion | 自定义 Model 树 | 内置 OT | 官方提供 Vue/React 封装 |
| **ProseMirror** | Model-View | 自定义 Model（Node/Mark） | 需要自己实现（y-prosemirror 等） | 框架无关，纯 JS |
| **TipTap** | 基于 ProseMirror 封装 | 同 ProseMirror | 通过扩展支持 | Vue/React 原生支持 |
| **Slate** | Model-View | JSON 树 | 需要自己实现 | React 原生，其他框架需要适配 |
| **Quill** | Delta 模型 | Delta（操作序列） | 内置（通过 Quill-Cursors） | 框架无关 |
| **Draft.js** | Model-View | ContentState（Immutable） | 需要自己实现 | 仅 React |
| **TinyMCE 6+** | 混合架构 | 自定义 Model | 商业版支持 | 官方提供 Vue/React 封装 |
| **Tiptap** | 基于 ProseMirror | 同 ProseMirror | yjs 扩展 | Vue/React 都支持 |

### 4. Selection 和 Range

浏览器原生的 Selection/Range API 是富文本编辑器的核心基础。

```js
// 获取当前选区
const selection = window.getSelection();
const range = selection.getRangeAt(0);

// Range 常用属性
range.startContainer;  // 选区起始节点
range.startOffset;     // 起始偏移量
range.endContainer;    // 选区结束节点
range.endOffset;       // 结束偏移量
range.collapsed;       // 是否为光标（起止点相同）

// 创建选区
const newRange = document.createRange();
newRange.setStart(node, offset);
newRange.setEnd(node, offset);
selection.removeAllRanges();
selection.addRange(newRange);
```

**现代编辑器的做法**：不直接用浏览器 Selection，而是在 Model 层维护自己的选区（如 CKEditor 5 的 `model.DocumentSelection`），然后同步到浏览器 Selection。这样做的好处是选区跟随数据模型，不依赖 DOM 结构。

### 5. 协同编辑

多人同时编辑一篇文档时，需要解决冲突问题。主流方案：

#### OT（Operational Transformation）

将每次编辑操作转换为 Operation（如 `insert`、`delete`、`retain`），服务端对并发操作做转换（transform），保证最终一致。

```
用户A：insert "Hello" at position 5
用户B：insert "World" at position 3
服务端：需要 transform 后的两个操作都能正确应用
```

代表：Google Docs、CKEditor 5（内置）

#### CRDT（Conflict-free Replicated Data Type）

数据结构本身保证合并无冲突，不需要中心服务器做转换。

代表：Yjs（用于 ProseMirror、TipTap）、Automerge

#### 对比

| 对比 | OT | CRDT |
|------|----|------|
| 实现复杂度 | 高（需要 transform 函数） | 低（数据结构保证） |
| 网络开销 | 小（只传操作） | 较大（需要维护元数据） |
| 中心化 | 需要中心服务器 | 可以去中心化 |
| 代表 | Google Docs、CKEditor 5 | Yjs、Automerge |

### 6. Delta 格式（Quill）

Quill 使用 Delta 格式描述文档内容和操作：

```js
// 文档内容
{
  ops: [
    { insert: 'Hello ' },
    { insert: 'World', attributes: { bold: true } },
    { insert: '\n' }
  ]
}

// 操作（用于协同）
{
  ops: [
    { retain: 6 },                    // 跳过前 6 个字符
    { insert: 'Beautiful ' },         // 插入文本
    { delete: 5 }                     // 删除 5 个字符
  ]
}
```

Delta 的特点是：操作可组合、可逆、可 transform（用于 OT 协同）。

### 7. 粘贴处理

富文本编辑器的粘贴是高频且复杂的问题：

1. **纯文本粘贴**：直接插入文本，去掉所有格式
2. **富文本粘贴**（从 Word/网页复制）：需要清洗 HTML，保留允许的格式
3. **图片粘贴**：`clipboardData.files` 获取图片，转成 base64 或上传后插入

```js
// 监听粘贴事件
editor.editing.view.document.on('clipboardInput', (evt, data) => {
  const htmlContent = data.dataTransfer.getData('text/html');
  if (htmlContent) {
    // 解析 HTML，清洗后插入
    data.content = parseAndSanitize(htmlContent);
  }
});
```

关键挑战：
- Word 粘贴的 HTML 有大量垃圾标签和内联样式
- 不同浏览器剪贴板数据格式不同
- 需要平衡"保留格式"和"安全"

### 8. IME（输入法）处理

中文、日文等输入法在 Composition 事件期间会临时修改 DOM，编辑器需要正确处理：

- `compositionstart`：输入法开始，编辑器应暂停对 DOM 的监听
- `compositionupdate`：输入法选字过程中，每次候选变化都会触发
- `compositionupdate` → `compositionend`：输入法确认，编辑器恢复监听

常见坑：
- 在 composition 期间触发了 model 更新，导致输入法候选框消失
- composition 期间的 DOM 变化被编辑器当作非法操作回滚

现代编辑器的做法：在 `compositionstart` 和 `compositionend` 之间暂停 model 同步，等输入法结束后统一处理。

---

### 9. 图片与大文件处理

- **内联 base64**：简单但会让 HTML 体积膨胀，适合临时预览
- **上传后插入 URL**：异步上传，插入 `<img src="url">`
- **懒加载**：大文档中图片不在可视区域时不加载
- **预览缩略图**：上传时生成缩略图，点击查看大图

### 10. 性能优化

#### 虚拟渲染

大文档场景下，只渲染可视区域的节点，类似虚拟列表。ProseMirror 通过 `decorations` + IntersectionObserver 实现。

#### 增量更新

不每次修改都重新渲染整个文档，只更新变化的部分。CKEditor 5 的 Downcast 就是增量的，只处理 model 变更的部分。

#### 操作批处理

多次 model 操作合并为一次渲染：

```js
// CKEditor 5
editor.model.change(writer => {
  writer.insertText('a', position1);
  writer.insertText('b', position2);
  // 批量操作，只触发一次 downcast
});
```

#### 防抖/节流

对高频事件（input、selectionchange）做节流，避免频繁触发 model 更新。

## 常见追问

1. contentEditable 有什么问题？为什么现代编辑器都不直接用它？
2. 为什么要做独立的 Model 层，直接操作 DOM 不行吗？
3. 富文本编辑器的协同编辑怎么实现的？OT 和 CRDT 有什么区别？
4. 粘贴 Word 内容怎么处理？为什么要清洗 HTML？
5. 输入法（IME）在编辑器里有什么坑？
6. 大文档场景下编辑器性能怎么优化？
7. 撤销/重做怎么实现的？操作栈 vs 快照？
8. 如何保证编辑器输出的 HTML 干净、安全？（XSS 防护）

## 回答要点

### 撤销/重做实现

两种方案：

**操作栈（主流）**：记录每次操作的正向和反向操作，撤销时执行反向，重做时执行正向。
- CKEditor 5：`Operation` 对象有 `undo()` 方法
- Quill：Delta 可逆操作

**快照**：每次操作保存一份完整文档快照，撤销时回退到上一个快照。
- 实现简单，但内存开销大，不适合大文档

### 输出安全

编辑器输出的 HTML 需要做 XSS 防护：
- 白名单过滤：只允许特定标签和属性
- 移除 `javascript:` 协议、`onclick` 等事件属性
- 对用户输入做转义
- 后端二次校验，不信任前端传入的 HTML
