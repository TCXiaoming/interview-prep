# 微前端常见面试题

## 1. 你们项目的微前端方案是怎么选的？为什么选 qiankun / single-spa？

**参考回答**：

选型要看实际需求，不能为了用微前端而用微前端。

主要考虑几个维度：
- **隔离需求**：如果子应用之间不需要严格隔离（比如都是自己团队的），single-spa 就够了。如果接入的是不同团队甚至不同公司的应用，需要 qiankun 的沙箱隔离
- **技术栈**：如果全是 React 且版本统一，Module Federation 最合适，共享依赖性能最好。如果 Vue/React 混合，qiankun 兼容性更好
- **部署方式**：子应用是否独立部署、独立 CI/CD？qiankun 和 single-spa 都支持，Module Federation 对构建工具依赖更强
- **团队规模**：小团队 3-5 人没必要上微前端，路由懒加载就够了。微前端解决的是 10+ 人团队协作的问题

## 2. qiankun 的 JS 沙箱是怎么实现的？有什么缺点？

**参考回答**：

qiankun 提供三种沙箱模式：

**LegacySandbox（单例沙箱）**：
- 用一个 Proxy 代理 window，`has` trap 让子应用以为自己在操作真实 window
- 实际上 set 操作记录到一个 `updatedValueSet` 里，get 操作先查更新集合，没有才 fallback 到真实 window
- 切换子应用时，根据 diff 还原 window 状态

**ProxySandbox（多例沙箱）**：
- 每个子应用一个 fakeWindow（`Object.create(null)`），完全隔离
- get 操作 fallback 到真实 window（只读），set 操作写到自己的 fakeWindow
- 支持同时运行多个子应用

**SnapshotSandbox**：
- 激活前对 window 拍快照，失活时 diff 还原
- 兼容不支持 Proxy 的浏览器（IE），但只支持单实例

**缺点**：
- 无法拦截所有全局 API，比如 `document.getElementById` 还是操作真实 DOM
- `MutationObserver`、`IntersectionObserver` 等新 API 可能没覆盖
- 事件监听器的清理依赖框架，如果子应用没正确卸载，会泄漏

## 3. 微前端的 CSS 隔离有哪些方案？各自的优缺点？

**参考回答**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| CSS Modules | 构建时给类名加 hash 后缀 | 零运行时成本 | 只防类名冲突，不防全局样式 |
| BEM 命名规范 | 人为约定命名空间 | 简单 | 依赖自觉，容易被破坏 |
| Shadow DOM | 浏览器原生隔离 | 真正的隔离 | 全局样式（body、html）无法穿透，弹窗类组件（Modal、Tooltip）挂载到 body 后脱离 Shadow DOM |
| 动态样式表 | 子应用激活时插入 style，失活时移除 | 兼容性好 | 切换瞬间可能闪屏（FOUC） |
| Scoped CSS | 给子应用每个选择器加容器前缀 | 比动态样式表稳定 | 解析 CSS 正则替换，可能有边界 case |

**qiankun 的做法**：Scoped CSS + 动态样式表组合。给子应用最外层容器加一个 `div[data-qiankun="子应用名"]`，然后把子应用 CSS 的所有选择器前面加上这个前缀，实现作用域限定。

**实际踩坑**：Shadow DOM 方案最"干净"但坑最多。比如 Ant Design 的 Modal 默认 `getPopupContainer` 是 `document.body`，弹窗内容会跑到 Shadow DOM 外面，样式丢失。需要手动配置 `getPopupContainer={() => container}` 让弹窗渲染在 Shadow DOM 内部。

## 4. 子应用之间怎么通信？你遇到过什么坑？

**参考回答**：

通信方式按耦合度从低到高：
1. **URL 参数 / 路由**：最解耦，天然支持浏览器前进后退，但只能传简单数据
2. **全局状态（GlobalState）**：类似 Redux 的 store，主应用维护，子应用订阅
3. **自定义事件**：`CustomEvent`，适合一对多的广播场景
4. **props 传递**：最直接，但耦合度最高，主应用要知道子应用内部需要什么

**遇到的坑**：
- **时序问题**：子应用 B 先加载完开始监听事件，子应用 A 后加载完才发事件——B 收不到。解决办法：GlobalState 有初始值 + onGlobalStateChange 的 `immediate` 参数
- **数据不可变**：一个子应用改了 GlobalState，另一个子应用的回调拿到的是引用，直接改对象会绕过框架检测。解决办法：深拷贝或约定 immutable 更新
- **跨域通信**：子应用部署在不同域名下，不能直接共享 GlobalState。用 postMessage 或统一后端网关下发 token

## 5. Module Federation 和 qiankun 的区别是什么？各自适合什么场景？

**参考回答**：

**Module Federation（MF）**：
- 核心能力：构建时/运行时从远程加载 JS 模块并共享依赖
- 不做 JS/CSS 隔离，所有代码跑在同一个 window 下
- 依赖 Webpack 5（或 Vite 插件），构建配置较重
- 适合：同团队内、技术栈统一、需要大量共享组件/工具函数的场景

**qiankun**：
- 核心能力：运行时加载子应用（通过 HTML 入口）+ 沙箱隔离 + 生命周期管理
- 做 JS/CSS 隔离，子应用之间互不影响
- 不依赖构建工具，子应用可以是任意技术栈
- 适合：不同团队、不同技术栈、需要独立部署独立发布的场景

**一个形象的比喻**：MF 像"图书馆"，大家共享书（模块），但都在一个房间里。qiankun 像"办公楼"，每家公司（子应用）有自己的办公室（沙箱），共享大厅（主应用）。

**可以组合使用**：主应用用 qiankun 管理子应用，子应用内部用 MF 共享公共组件。

## 6. 微前端的子应用静态资源路径有问题，怎么处理？

**参考回答**：

问题本质：子应用部署在 `https://sub.example.com`，但在主应用 `https://main.example.com` 里加载时，CSS 里的 `url(./img/logo.png)` 会解析成 `https://main.example.com/img/logo.png`，404。

**解决方案**：

```js
// 方案 1：Webpack 配置 publicPath（构建时）
// 子应用 webpack.config.js
output: {
  publicPath: 'https://sub.example.com/', // 绝对路径
}

// 方案 2：运行时动态设置
// 子应用入口文件
if (window.__POWERED_BY_QIANKUN__) {
  __webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__;
}
// qiankun 会在加载子应用时注入子应用的 entry URL

// 方案 3：用 CSS 变量 + base 标签
// 子应用 HTML 里加 <base href="https://sub.example.com/">
```

**qiankun 自动处理的部分**：
- HTML 中的 `<script src>`、`<link href>`、`<img src>`：会自动加上子应用的 base URL
- 内联 JS 里的 `__webpack_public_path__`：需要子应用自己配合

**坑**：如果子应用有运行时从后端获取的图片 URL（非构建产物），这些不在 qiankun 的处理范围内，需要子应用自己拼完整路径。

## 7. 如何实现微前端的预加载？有什么好处和风险？

**参考回答**：

**原理**：在浏览器空闲时（`requestIdleCallback`），提前请求子应用的 JS/CSS 资源并缓存到浏览器。等用户真正点击导航时，资源已经在缓存里了，加载速度接近零等待。

```js
// qiankun 的预加载
start({ prefetch: 'all' }); // 预加载所有子应用
start({ prefetch: ['app1', 'app2'] }); // 只预加载指定子应用
```

**好处**：
- 用户点击子应用导航时秒开，体验接近单体应用
- 利用浏览器空闲时间，不影响首屏渲染

**风险**：
- 首屏流量增大：用户可能根本不会访问某些子应用，白加载了
- 移动端流量敏感：在 4G 环境下预加载所有子应用可能消耗用户流量
- 缓存失效问题：子应用更新了，但用户浏览器缓存还是旧版本。需要配合版本号或文件 hash

**实际做法**：
- PC 端 B 管理后台：`prefetch: 'all'` 问题不大，用户大概率都会用到
- 移动端 / 面向 C 端：只预加载高频子应用，或者基于用户行为预测（比如进了 A 页面大概率会进 B）
- 配合 Service Worker 做离线缓存，效果更好

## 8. 微前端子应用怎么独立开发调试？不启动主应用能跑吗？

**参考回答**：

**必须能独立运行**，这是微前端的基本要求，否则开发效率会很差。

**qiankun 的做法**：

```js
// 子应用入口判断是否在微前端环境下
if (!window.__POWERED_BY_QIANKUN__) {
  // 独立运行时，自己 render
  render({});
}

export async function mount(props) {
  render(props); // 微前端环境下，由主应用触发
}

function render(props) {
  const { container } = props;
  ReactDOM.render(
    <App />,
    container ? container.querySelector('#root') : document.querySelector('#root')
  );
}
```

**关键点**：
- 子应用要有兜底逻辑：判断 `window.__POWERED_BY_QIANKUN__`，没有就独立 render
- 容器挂载点要区分：独立运行挂 `document.querySelector('#root')`，微前端环境下挂 `container.querySelector('#root')`（qiankun 会给一个 shadow DOM 容器）
- 路由 base path：独立运行时 base 是 `/`，微前端环境下可能是 `/app1/`，需要动态设置

**Webpack 配置**：
```js
// 子应用 webpack dev server 配置 headers 允许跨域
devServer: {
  headers: {
    'Access-Control-Allow-Origin': '*', // 主应用跨域加载子应用资源
  },
},
```

## 9. 和微前端相比，Monorepo 解决的是什么问题？两者能组合吗？

**参考回答**：

**区别**：
- **Monorepo**：代码管理方式，多个项目/包在一个 Git 仓库里，用 pnpm workspace / Turborepo / Nx 管理依赖和构建
- **微前端**：运行时架构，多个应用在一个浏览器页面里运行，解决隔离、通信、部署的问题

**本质不同**：Monorepo 解决的是"代码怎么组织"，微前端解决的是"应用怎么运行"。

**可以组合**：比如用 Monorepo 管理主应用 + 所有子应用的代码，共享 TypeScript 类型定义、公共工具函数、UI 组件。但每个子应用还是独立构建、独立部署，运行时由 qiankun 加载。

```
monorepo/
├── packages/
│   ├── main-app/          # 主应用
│   ├── sub-app-order/     # 子应用：订单
│   ├── sub-app-user/      # 子应用：用户中心
│   ├── shared-utils/      # 共享工具函数
│   └── shared-types/      # 共享类型定义
└── package.json
```

**什么时候只用 Monorepo 不用微前端**：团队小（5 人以内）、应用之间耦合度高、不需要独立部署。路由懒加载 + code splitting 就够了，没必要上微前端。

## 10. 微前端在实际项目中你遇到过哪些坑？怎么解决的？

**参考回答**（可以挑选 2-3 个讲）：

**坑 1：子应用的定时器 / 事件监听没清理**
- 现象：切换子应用再切回来，发现有多个定时器在跑，页面卡顿
- 原因：子应用 `unmount` 时没清 `setInterval` 和 `addEventListener`
- 解决：封装一个 `useEffect` 的 cleanup 自动收集器，或者在 unmount 里手动清理。qiankun 提供了 `addErrorHandler` 做兜底

**坑 2：子应用的弹窗跑到主应用去了**
- 现象：Ant Design Modal 弹出来没有样式
- 原因：Modal 默认渲染到 `document.body`，脱离了子应用的 CSS 隔离范围
- 解决：配置 `getPopupContainer` 渲染到子应用容器内

**坑 3：主子应用之间路由冲突**
- 现象：主应用和子应用都用了 React Router，路由互相打架
- 原因：子应用的路由监听了全局 `popstate` 事件，和主应用冲突
- 解决：子应用设置 `routerBase`，history 实例用 `basename`；或者子应用用 `hash` 路由模式

**坑 4：子应用之间共享 CSS 变量不生效**
- 现象：主应用定义了 `--primary-color`，子应用在 Shadow DOM 里读不到
- 原因：CSS 自定义属性不能穿透 Shadow DOM 边界
- 解决：主应用通过 JS 注入变量到子应用，或者不用 Shadow DOM 隔离改用 Scoped CSS

**坑 5：keep-alive 场景下的状态丢失**
- 现象：子应用切换后再切回来，表单数据没了
- 原因：qiankun 默认走 mount/unmount 完整生命周期，每次切换都重新渲染
- 解决：用 `excludeApps` 配合自定义缓存逻辑，或者子应用内部做状态持久化（localStorage / sessionStorage）
