# 前端并发控制

## 核心概念

前端的"并发"不是多线程（JS 是单线程），而是指**多个异步任务的调度与管理**。常见场景：批量请求、表单重复提交、竞态条件、请求取消等。

---

## 1. Promise 并发原语

### 并行执行

```js
// Promise.all：全部成功才成功，一个失败就失败
const [users, posts] = await Promise.all([
  fetch('/api/users'),
  fetch('/api/posts')
])

// Promise.allSettled：全部执行完，不管成功失败（ES2020）
const results = await Promise.allSettled([
  fetch('/api/a'),
  fetch('/api/b')
])
// results: [{status:'fulfilled', value:...}, {status:'rejected', reason:...}]

// Promise.race：取第一个完成的（成功或失败）
const result = await Promise.race([
  fetch('/api/data'),
  new Promise((_, reject) => setTimeout(() => reject('timeout'), 5000))
])

// Promise.any：取第一个成功的（全部失败才失败，ES2021）
const fastest = await Promise.any([
  fetch('/cdn1/api'),
  fetch('/cdn2/api')
])
```

### 对比

| API | 成功条件 | 失败条件 | 适用场景 |
|-----|---------|---------|---------|
| `Promise.all` | 全部成功 | 任一失败 | 多个请求互相依赖 |
| `Promise.allSettled` | 全部完成 | 无（总是成功） | 批量操作，需要逐个判断结果 |
| `Promise.race` | 第一个完成 | 第一个完成 | 超时控制、竞速 |
| `Promise.any` | 第一个成功 | 全部失败 | 多源请求取最快 |

## 2. 并发数量控制

批量请求时不一次性发完，限制同时进行的请求数量，避免浏览器并发连接数限制（同域名 6 个）或服务端压力。

### 实现思路：池化调度

```js
async function concurrencyPool(tasks, limit) {
  const results = []
  const executing = new Set()

  for (const [index, task] of tasks.entries()) {
    const p = Promise.resolve().then(() => task())
    results[index] = p
    executing.add(p)

    const cleanup = () => executing.delete(p)
    p.then(cleanup, cleanup)

    if (executing.size >= limit) {
      await Promise.race(executing) // 等任意一个完成
    }
  }

  return Promise.all(results)
}

// 使用
const urls = Array.from({ length: 100 }, (_, i) => `/api/item/${i}`)
const tasks = urls.map(url => () => fetch(url))
const results = await concurrencyPool(tasks, 5) // 最多 5 个并发
```

### 核心机制

- 维护一个 `executing` Set 记录正在执行的任务
- 每次新增任务前检查是否达到上限
- 达到上限时用 `Promise.race` 等任意一个完成再继续

## 3. 请求去重

短时间内相同请求只发一次，后续请求复用同一个 Promise。

### 实现

```js
const pendingRequests = new Map()

function dedupedFetch(url, options) {
  const key = `${options?.method || 'GET'}:${url}`

  if (pendingRequests.has(key)) {
    return pendingRequests.get(key) // 复用已有请求
  }

  const promise = fetch(url, options)
    .finally(() => pendingRequests.delete(key)) // 请求完成后清除缓存

  pendingRequests.set(key, promise)
  return promise
}

// 用户快速点击 3 次，实际只发 1 个请求
dedupedFetch('/api/user')
dedupedFetch('/api/user')
dedupedFetch('/api/user') // 3 个调用共享同一个 Promise
```

### 适用场景

- 表单重复提交
- 列表页快速切换 tab，旧请求未完成时又触发新请求
- 多个组件同时请求同一接口

## 4. 请求取消

用户快速切换页面或搜索时，取消未完成的旧请求，避免结果覆盖。

### AbortController（标准方案）

```js
let controller = null

async function search(query) {
  // 取消上一次请求
  if (controller) {
    controller.abort()
  }

  controller = new AbortController()

  try {
    const res = await fetch(`/api/search?q=${query}`, {
      signal: controller.signal
    })
    const data = await res.json()
    return data
  } catch (err) {
    if (err.name === 'AbortError') {
      console.log('请求已取消') // 不处理结果
      return
    }
    throw err
  }
}

// 用户快速输入 "abc"、"abcd"、"abcde"
// "abc" 的请求被取消，"abcd" 的请求被取消，只处理 "abcde" 的结果
```

### Vue 中的实践

```js
// 组合式函数
function useSearch() {
  let controller = null

  async function search(query) {
    controller?.abort()
    controller = new AbortController()

    try {
      const res = await fetch(`/api/search?q=${query}`, {
        signal: controller.signal
      })
      return await res.json()
    } catch (e) {
      if (e.name !== 'AbortError') throw e
    }
  }

  onUnmounted(() => controller?.abort()) // 组件销毁时取消
  return { search }
}
```

## 5. 竞态条件（Race Condition）

多个异步操作以不确定的顺序完成，导致结果不一致。

### 典型场景

```js
// 用户快速点击"下一页"
let currentPage = 1

async function loadPage(page) {
  currentPage = page
  const data = await fetch(`/api/list?page=${page}`) // 假设第 2 页先返回
  renderList(data)
}

// 点击第 2 页，再点击第 3 页
loadPage(2) // 发出请求
loadPage(3) // 发出请求
// 如果第 2 页的响应比第 3 页晚到达，页面会显示第 2 页的数据，但 currentPage 是 3
```

### 解决方案

**方案一：请求取消（推荐）**

```js
let controller = null

async function loadPage(page) {
  controller?.abort()
  controller = new AbortController()

  const data = await fetch(`/api/list?page=${page}`, {
    signal: controller.signal
  }).then(r => r.json())

  renderList(data)
}
```

**方案二：版本号 / Token**

```js
let requestId = 0

async function loadPage(page) {
  const id = ++requestId
  const data = await fetch(`/api/list?page=${page}`).then(r => r.json())

  // 只有最新的请求才更新 UI
  if (id === requestId) {
    renderList(data)
  }
}
```

**方案三：闭包**

```js
function createLoader() {
  let loading = false

  return async function load(page) {
    if (loading) return // 忽略并发调用
    loading = true
    try {
      const data = await fetch(`/api/list?page=${page}`)
      renderList(data)
    } finally {
      loading = false
    }
  }
}
```

## 6. 串行执行

多个异步任务按顺序依次执行，前一个完成后再执行下一个。

```js
// 方案一：for...of + await
async function serial(tasks) {
  const results = []
  for (const task of tasks) {
    results.push(await task())
  }
  return results
}

// 方案二：reduce 链式
function serialReduce(tasks) {
  return tasks.reduce(
    (chain, task) => chain.then(results => task().then(r => [...results, r])),
    Promise.resolve([])
  )
}
```

## 7. 重试机制

请求失败后自动重试，通常配合退避策略。

```js
async function fetchWithRetry(url, options = {}, maxRetries = 3) {
  for (let i = 0; i <= maxRetries; i++) {
    try {
      const res = await fetch(url, options)
      if (!res.ok) throw new Error(res.statusText)
      return await res.json()
    } catch (err) {
      if (i === maxRetries) throw err
      // 指数退避：1s, 2s, 4s
      await new Promise(r => setTimeout(r, 1000 * 2 ** i))
    }
  }
}
```

### 退避策略

- **固定间隔**：每次等 1s
- **线性增长**：1s, 2s, 3s, 4s
- **指数退避**：1s, 2s, 4s, 8s（推荐，避免同时重试打垮服务端）
- **随机抖动**：在退避基础上加随机值，避免多个客户端同时重试

## 8. Mutex（互斥锁）

保证同一时间只有一个操作在执行，常用于防止并发写冲突。

```js
class Mutex {
  constructor() {
    this.queue = []
    this.locked = false
  }

  async acquire() {
    if (!this.locked) {
      this.locked = true
      return
    }
    return new Promise(resolve => this.queue.push(resolve))
  }

  release() {
    if (this.queue.length > 0) {
      const next = this.queue.shift()
      next() // 唤醒下一个等待者
    } else {
      this.locked = false
    }
  }
}

// 使用：保证余额扣减串行执行
const mutex = new Mutex()

async function deductBalance(amount) {
  await mutex.acquire()
  try {
    const balance = await getBalance()
    await setBalance(balance - amount)
  } finally {
    mutex.release()
  }
}
```

## 9. 前端乐观锁 vs 悲观锁

### 悲观锁

操作前先加锁，防止其他操作干扰。适合强一致性场景。

```
用户点击保存 → 请求加锁 → 修改数据 → 释放锁
```

### 乐观锁

不加锁，提交时检查版本号是否冲突。适合高并发读场景。

```
用户编辑数据（携带版本号 v1）→ 提交时检查版本号
  → v1 仍是最新 → 保存成功
  → v1 已过期（别人改过了）→ 提示冲突，让用户决定
```

```js
async function saveWithOptimisticLock(data) {
  const current = await fetch(`/api/item/${data.id}`).then(r => r.json())

  const res = await fetch(`/api/item/${data.id}`, {
    method: 'PUT',
    body: JSON.stringify({
      ...data,
      version: current.version // 携带版本号
    })
  })

  if (res.status === 409) {
    // 版本冲突
    const latest = await res.json()
    throw new ConflictError('数据已被其他人修改', latest)
  }

  return res.json()
}
```

## 常见追问

1. `Promise.all` 和 `Promise.allSettled` 的区别？什么时候用哪个？
2. 如何控制并发请求数量？
3. 用户快速搜索时怎么处理竞态条件？
4. `AbortController` 的原理是什么？能取消所有类型的请求吗？
5. 请求去重怎么实现？
6. 重试机制的退避策略有哪些？为什么用指数退避？
7. 乐观锁和悲观锁分别适合什么场景？
8. `Promise.race` 和 `Promise.any` 的区别？

## 回答要点

### AbortController 原理

`AbortController` 是浏览器原生 API，通过 `signal` 属性传递给 `fetch`。调用 `abort()` 时，signal 状态变为 aborted，fetch 内部检查到后抛出 `AbortError`。

只能取消支持 `signal` 参数的 API（fetch、ReadableStream 等），不能取消 `XMLHttpRequest`（需要用 `xhr.abort()`）。

### 为什么用指数退避

- 多个客户端同时重试会形成"惊群效应"，瞬间打垮服务端
- 指数退避让重试间隔逐渐增大，给服务端恢复时间
- 加随机抖动（jitter）进一步分散重试时间
