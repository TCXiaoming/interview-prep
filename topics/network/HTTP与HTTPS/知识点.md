# HTTP 与 HTTPS

## 核心概念

### HTTP 协议演进

| 版本 | 年份 | 关键特性 |
|---|---|---|
| HTTP/1.1 | 1997 | 持久连接、管道化（实际未普及）、Host 头 |
| HTTP/2 | 2015 | 二进制分帧、多路复用、头部压缩（HPACK）、服务器推送 |
| HTTP/3 | 2022 | 基于 QUIC（UDP）、0-RTT 连接建立、连接迁移 |

### HTTP/1.1 的问题与解决方案

**队头阻塞（Head-of-Line Blocking）：**
- 同一 TCP 连接上，前一个请求阻塞后面所有请求
- 浏览器限制同域 6 个连接来缓解，但不根本解决
- 雪碧图、合并文件、域名分片是这个时代的产物

**HTTP/2 的改进：**
- **多路复用** — 一个 TCP 连接上并行传输多个请求/响应，解决了 HTTP 层的队头阻塞
- **二进制分帧** — 数据以帧为单位传输，解析更快
- **头部压缩** — HPACK 算法压缩重复的请求头
- **服务器推送** — 服务端可以主动推送资源（实际用得不多）

**HTTP/2 的遗留问题：**
- TCP 层的队头阻塞 — 一个 TCP 包丢失，整个连接等待重传
- TCP 握手 + TLS 握手延迟

**HTTP/3 的改进：**
- **基于 QUIC（UDP）** — 不再依赖 TCP，解决 TCP 层队头阻塞
- **0-RTT** — 首次连接可以不等待握手完成就发送数据
- **连接迁移** — 从 WiFi 切到 4G，连接不中断（用 Connection ID 代替 IP + Port）
- **内置加密** — TLS 1.3 内置在 QUIC 中，不是叠加层

### HTTPS

**TLS 握手过程（TLS 1.2）：**
```
Client                          Server
  |------ Client Hello --------->|  支持的加密套件、随机数
  |<----- Server Hello ----------|  选定的加密套件、随机数
  |<----- Certificate -----------|  服务端证书
  |<----- Server Key Exchange ---|  服务端公钥
  |<----- Server Hello Done -----|
  |------ Client Key Exchange -->|  客户端公钥
  |------ Change Cipher Spec --->|
  |------ Finished ------------->|
  |<----- Change Cipher Spec ----|
  |<----- Finished --------------|
  |====== 加密通信开始 ==========|
```

**TLS 1.3 改进：**
- 握手从 2-RTT 减少到 1-RTT
- 支持 0-RTT（恢复会话时）
- 移除不安全的加密算法（RSA、CBC、SHA-1）
- 只支持 ECDHE 密钥交换（前向安全性）

### 常见状态码

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| 200 | 成功 | 正常请求 |
| 301 | 永久重定向 | HTTP → HTTPS、域名更换 |
| 302 | 临时重定向 | 登录跳转 |
| 304 | Not Modified | 协商缓存命中 |
| 400 | Bad Request | 参数格式错误 |
| 401 | Unauthorized | 未登录 |
| 403 | Forbidden | 无权限 |
| 404 | Not Found | 资源不存在 |
| 429 | Too Many Requests | 限流 |
| 500 | Internal Server Error | 服务端异常 |
| 502 | Bad Gateway | 网关/代理错误 |
| 503 | Service Unavailable | 服务不可用（维护中） |

### 缓存策略

```
请求 → 强缓存命中？ → 是 → 直接用缓存
                    → 否 → 协商缓存 → 304？→ 是 → 用缓存
                                        → 否 → 200 + 新资源
```

**强缓存：**
- `Cache-Control: max-age=31536000`（优先级高）
- `Expires: Thu, 01 Dec 2025 16:00:00 GMT`（HTTP/1.0，用绝对时间）

**协商缓存：**
- `ETag` + `If-None-Match`（内容哈希，优先级高）
- `Last-Modified` + `If-Modified-Since`（修改时间，精度到秒）

**前端资源缓存策略：**
- HTML — `no-cache`（每次都协商，确保拿到最新入口）
- JS/CSS（带 hash）— `max-age=31536000, immutable`（文件名变了就是新资源）
- 图片 — `max-age=86400` 或更长
- API 接口 — `no-store`（不缓存）或短时间 `max-age`

## 常见追问

### Q: HTTP/2 已经多路复用了，为什么还需要 HTTP/3？

**回答要点：**
HTTP/2 解决了 HTTP 层的队头阻塞，但底层还是 TCP。TCP 是字节流协议，一个包丢失会导致整个连接等待重传，所有流都被阻塞。HTTP/3 用 QUIC（基于 UDP），每个流独立，一个流丢包不影响其他流。

### Q: TLS 1.3 的 0-RTT 有什么安全风险？

**回答要点：**
0-RTT 数据没有前向安全性保障，可能被重放攻击（Replay Attack）。所以 0-RTT 只能用于幂等请求（GET），不能用于非幂等请求（POST）。银行等安全敏感场景通常禁用 0-RTT。

### Q: 强缓存和协商缓存怎么配合使用？

**回答要点：**
实际项目中，用文件名 hash 来区分版本：
- `app.abc123.js` → 强缓存 1 年，因为内容变了文件名就变了
- `index.html` → 协商缓存，确保用户总能拿到最新的入口文件引用

这就是为什么 Webpack/Vite 打包出来的文件名带 hash。

## 回答要点总结

1. HTTP 协议演进要能说清楚每一代解决了什么问题
2. TLS 握手过程不需要背到每个字节，但关键步骤要说清楚
3. 缓存策略是高频考点，强缓存 vs 协商缓存要能说清区别和使用场景
4. HTTP/3 和 QUIC 是加分项
