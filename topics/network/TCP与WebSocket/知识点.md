# TCP 与 WebSocket

## 核心概念

### TCP 三次握手

```
Client                  Server
  |---- SYN (seq=x) --->|     第一次握手：客户端发 SYN，服务端确认客户端发送能力
  |<--- SYN+ACK ------- |     第二次握手：服务端回 SYN+ACK，客户端确认双方收发能力
  |---- ACK (seq=y) --->|     第三次握手：客户端发 ACK，服务端确认客户端接收能力
```

**为什么是三次不是两次？**
- 防止历史连接：如果客户端发了一个旧的 SYN 包，两次握手会让服务端直接建立连接并分配资源，浪费
- 同步双方初始序列号：双方都需要确认对方的序列号

### TCP 四次挥手

```
Client                  Server
  |---- FIN ----------->|     客户端：我没数据发了
  |<--- ACK ------------|     服务端：收到，我可能还有数据
  |<--- FIN ------------|     服务端：我也没数据了
  |---- ACK ----------->|     客户端：收到，连接关闭
```

**为什么是四次不是三次？**
- TCP 是全双工的，关闭发送和接收要分开确认
- 服务端收到 FIN 后可能还有数据要发，不能立即发 FIN

**TIME_WAIT 状态：**
- 主动关闭方会进入 TIME_WAIT，持续 2 * MSL（Maximum Segment Lifetime）
- 作用 1：确保最后一个 ACK 能到达服务端（如果丢了，服务端会重发 FIN）
- 作用 2：确保旧连接的残留数据包在网络中消亡，不会影响新连接

### WebSocket

**为什么需要 WebSocket？**
- HTTP 是请求-响应模式，服务端不能主动推送
- 轮询（Polling）浪费资源，长轮询（Long Polling）有延迟
- WebSocket 建立连接后，双方可以随时双向通信

**WebSocket 握手（基于 HTTP 升级）：**
```
客户端请求：
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务端响应：
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

**WebSocket vs SSE（Server-Sent Events）：**

| 维度 | WebSocket | SSE |
|---|---|---|
| 通信方向 | 双向 | 单向（服务端→客户端） |
| 协议 | ws:// / wss:// | HTTP |
| 断线重连 | 需要自己实现 | 浏览器自动重连 |
| 数据格式 | 二进制/文本 | 文本 |
| 适用场景 | 实时聊天、游戏、协作编辑 | 通知推送、AI 流式输出、实时更新 |

### WebSocket 心跳机制

```js
// 客户端心跳
class WSClient {
  startHeartbeat() {
    this.heartbeatTimer = setInterval(() => {
      if (this.ws.readyState === WebSocket.OPEN) {
        this.ws.send(JSON.stringify({ type: 'ping' }));
        // 设置超时，如果服务端没回 pong 就断线重连
        this.pongTimeout = setTimeout(() => {
          this.reconnect();
        }, 5000);
      }
    }, 30000);
  }

  onMessage(data) {
    if (data.type === 'pong') {
      clearTimeout(this.pongTimeout); // 收到 pong，清除超时
    }
  }
}
```

**为什么需要心跳？**
1. 检测连接是否还活着（网络断开时 TCP 不一定能及时感知）
2. 防止代理/负载均衡器因为空闲而断开连接（Nginx 默认 60s 空闲超时）
3. 保持 NAT 映射（某些网络环境下长时间空闲会导致 NAT 表项被清除）

## 常见追问

### Q: WebSocket 连接断了怎么处理？

**回答要点：**
1. **心跳检测** — 定期发 ping/pong，超时未响应则判定断线
2. **指数退避重连** — 断线后重连，间隔逐渐增大（1s → 2s → 4s → 8s），避免服务器被压垮
3. **消息队列** — 断线期间的消息暂存本地，重连后补发
4. **状态同步** — 重连后拉取断线期间的增量数据

### Q: WebSocket 在微前端/多 tab 场景下怎么管理？

**回答要点：**
- 多个 tab 都连 WebSocket 浪费资源，可以用 SharedWorker 共享一个连接
- 或者用 BroadcastChannel 让多个 tab 通信，一个 tab 持有连接，收到消息后广播给其他 tab
- 微前端场景下，各子应用不要各自建连接，由主应用统一管理

### Q: 什么时候用 WebSocket，什么时候用 HTTP？

**回答要点：**
- **实时性要求高 + 双向通信** → WebSocket（聊天、协作编辑、游戏）
- **实时性要求不高 + 单向推送** → SSE 或轮询（通知、AI 流式输出）
- **常规 CRUD** → HTTP REST API（大部分业务场景）
- 不要为了用 WebSocket 而用 WebSocket，HTTP 简单可靠，大部分场景够用

## 回答要点总结

1. TCP 三次握手/四次挥手要能说清每一步的目的
2. WebSocket 的心跳机制是重点，面试爱问
3. WebSocket vs SSE vs 轮询的适用场景要清楚
4. 实际项目中的 WebSocket 管理（重连、消息队列、多 tab）是加分项
